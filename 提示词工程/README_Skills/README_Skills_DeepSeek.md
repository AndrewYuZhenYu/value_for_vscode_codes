# README 编写规范

你需要为当前项目编写一份**专业、完整、准确、可长期维护**的 `README.md`。

这不是一份简单的项目简介，也不是机械套用 GitHub README 模板。你需要**先真正理解当前项目，再根据项目实际规模、功能、技术栈、代码结构、使用场景和开发复杂度，自主决定 README 的结构、深度和篇幅**。

README 的核心目标是：

> **让普通用户能够最快理解“这是什么、能做什么、怎么用”；让开发者能够充分理解“它是怎么实现的、各部分如何协作、为什么这样设计、如何继续开发和维护”。**

README 应当是一份真正服务于项目本身的文档，而不是为了满足某种固定格式而存在的模板。

---

# 一、最重要的总体原则

## 1. 必须以项目实际内容为依据

在开始编写 README 之前，必须尽可能充分地检查和理解当前项目。

根据项目情况，应当检查但不限于：

- 项目源代码；
- 项目完整目录结构；
- 程序入口；
- 配置文件；
- `requirements.txt`、`package.json`、`CMakeLists.txt` 等依赖或构建文件；
- 示例代码；
- 命令行参数；
- GUI 界面；
- API 接口；
- 数据文件；
- 测试代码；
- 脚本；
- 构建方式；
- 打包方式；
- 部署方式；
- LICENSE；
- 已有文档；
- 注释；
- 已有 README；
- 项目中的版本信息；
- 项目实际使用的第三方库；
- 项目实际支持的平台；
- 项目实际产生的输入和输出。

**不要根据项目名称、文件名称或少量代码猜测项目功能。**

README 中出现的：

- 功能；
- 命令；
- 参数；
- 文件名；
- 目录；
- API；
- 依赖；
- 运行方式；
- 架构关系；
- 技术细节；

都应尽可能能够从项目实际内容中得到依据。

如果某项信息无法确认：

- 不要擅自编造；
- 不要为了让 README 看起来完整而猜测；
- 可以直接省略；
- 如果确实有必要，可以明确标记为“待补充”或“当前项目未提供相关信息”。

**准确性永远优先于完整性。**

---

## 2. 绝对不要机械套用模板

这是本规范中非常重要的一条。

README **不是固定模板填空题**。

虽然下面会提供很多可以考虑的章节，但它们只是为了提醒你：

> **一个优秀的 README 通常可能需要考虑哪些方面。**

它们**不是强制目录，更不是固定顺序**。

你必须根据当前项目自行判断。

例如：

- 一个几十行的小工具，不需要写成几十页；
- 一个几百行的小型个人工具，应重点说明用途、安装和使用方式；
- 一个几千行的个人项目，需要适当说明核心功能、结构和实现；
- 一个几十个源文件、多个模块组成的项目，应提供较完整的架构和开发者文档；
- 一个库/API 项目，应重点说明安装、接口和调用方式；
- 一个命令行工具，应重点说明命令、参数、输入和输出；
- 一个 GUI 项目，应重点说明界面、操作流程、配置和结果；
- 一个数据处理项目，应重点说明输入、处理流程、输出格式；
- 一个网络服务，应重点说明接口、通信流程、部署和配置；
- 一个课程/学习项目，可以适当说明设计目的和学习内容，但不要把 README 写成课程实验报告；
- 一个内部个人工具，可能根本不需要贡献指南、路线图等章节。

**如果你认为当前项目不适合某个章节，可以直接不写。**

反过来，如果项目中存在本规范没有明确列出的重要内容，也应该主动增加相应章节。

**你按照自己的判断生成的结构，只要最符合当前项目实际情况，就是最好的结构。**

---

## 3. “详细”不等于“废话多”

这是非常重要的要求。

README 可以详细，而且对于复杂项目，应该足够详细。

但是绝对不要通过以下方式制造所谓的“详细”：

- 重复描述同一个功能；
- 使用大量空泛形容词；
- 反复解释显而易见的内容；
- 把代码逐行翻译成自然语言；
- 把所有函数都逐个解释一遍；
- 大段介绍与项目实际使用无关的背景知识；
- 使用大量“本项目具有……”“通过……可以……”等没有实际信息量的句子；
- 为了看起来专业而加入没有实际意义的章节；
- 为了满足固定字数而重复内容；
- 把项目中很简单的逻辑故意写得复杂。

应该优先增加**信息密度**。

例如：

> 一个真实参数、一个实际命令、一个准确的目录说明、一个真实输入输出示例、一个模块之间的依赖关系、一个关键设计原因，都比一大段空泛介绍更有价值。

**宁可增加有价值的技术信息，也不要增加没有信息量的文字。**

---

# 二、README 的核心读者

README 至少需要同时服务两类主要读者：

## 1. 普通用户

普通用户最关心：

1. 这是什么？
2. 能解决什么问题？
3. 有什么主要功能？
4. 需要什么环境？
5. 如何安装？
6. 如何运行？
7. 最简单的使用方法是什么？
8. 输入什么？
9. 输出什么？
10. 常见问题如何解决？

因此用户部分应该：

- 简洁；
- 直接；
- 可操作；
- 信息密度高；
- 尽量少讲内部实现；
- 避免让用户阅读大量开发者内容才能开始使用。

**普通用户应该能够在很短时间内完成第一次运行。**

---

## 2. 开发者

开发者最关心：

1. 项目如何组织？
2. 使用了什么技术？
3. 核心模块是什么？
4. 模块之间如何协作？
5. 程序从哪里开始执行？
6. 程序主要执行流程是什么？
7. 数据如何在模块之间流动？
8. 核心逻辑在哪里？
9. 关键设计为什么这样实现？
10. 如何增加功能？
11. 如何修改现有功能？
12. 如何替换某个模块？
13. 如何构建？
14. 如何测试？
15. 如何发布或部署？
16. 当前有什么限制？

因此开发者部分可以明显更加详细。

对于复杂项目，应根据实际情况提供：

- 项目结构；
- 技术栈；
- 系统架构；
- 模块说明；
- 执行流程；
- 数据流；
- 核心类和函数；
- 关键设计；
- 配置机制；
- 异常处理；
- 测试体系；
- 构建方式；
- 发布方式；
- 扩展方式；
- 已知限制。

---

# 三、README 的结构应当由项目决定

下面列出的章节只是**可选参考范围**，不是固定模板。

```text
# 项目名称

项目一句话简介

项目状态 / 版本 / 许可证 / 技术栈等必要信息

## 项目简介
## 主要功能
## 快速开始
## 安装与环境
## 使用方法
## 输入与输出
## 配置说明
## 项目结构
## 系统架构
## 核心模块
## 核心执行流程
## 数据流
## 技术实现
## 开发环境
## 构建与运行
## 测试
## 错误处理
## 常见问题
## 已知限制
## 扩展与二次开发
## 开发路线
## 参与开发
## 许可证
```

**不要机械照抄这个结构。**

例如，一个只有几十行代码的程序完全没有必要写：

```text
## 系统架构
## 数据流
## 开发路线
## 参与开发
```

如果这些内容没有实际价值，可以直接省略。

同样，如果一个复杂项目存在插件系统、数据库层、缓存层、配置系统、权限系统等重要组成部分，而上面的参考目录没有对应章节，就应该主动增加。

# 四、用户部分写作要求（**本版本重点强化**）

> 用户部分的核心目标：**让一个从未接触过该项目的人，在不阅读开发者章节、不翻阅源码的情况下，能够一步一步完成环境准备、安装、运行，并得到预期结果。**
>
> 因此，用户部分必须做到：**脉络清晰、步骤分明、可复制粘贴、可自我验证。**
>
> 本版本对用户部分的写作提出以下强化要求，与原有要求并不冲突，而是对原有要求的具体化和加强。

---

## 0. 用户部分的整体脉络（**必须体现**）

用户部分应当形成一个清晰的、从上到下依次推进的脉络：

```text
① 这是什么（项目简介）
   ↓
② 需要什么（环境要求）
   ↓
③ 一次性准备好环境（一键安装 / 完整依赖安装）
   ↓
④ 第一次运行（快速开始，最短路径）
   ↓
⑤ 验证是否成功（输入示例 → 输出示例）
   ↓
⑥ 更多用法（参数、配置、进阶）
   ↓
⑦ 遇到问题怎么办（常见问题）
```

用户只要按照这个顺序从上往下阅读，就应该能够从“完全不了解项目”走到“成功运行并得到结果”。

**不要打乱这个脉络。** 例如不要把“常见问题”放到“快速开始”之前，也不要把“配置说明”拆散到多个互相引用的位置，导致用户来回跳转。

---

## 1. 项目简介

README 开头应该在极短篇幅内回答：

> **这是什么？解决什么问题？主要面向谁？**

第一眼看到 README 的用户不应该需要阅读数百字才能知道项目用途。

可以采用：

```markdown
# 项目名称

一句话说明项目用途。

简短补充说明核心能力、主要使用场景以及项目定位。
```

不要在开头写大段背景故事。

---

## 2. 主要功能

只列出真正重要的功能。

例如：

```markdown
## 主要功能

- 功能 A：具体解决什么问题
- 功能 B：具体解决什么问题
- 功能 C：支持什么输入或输出
- 功能 D：提供什么特殊能力
```

避免：

```text
- 简单易用
- 功能强大
- 高效稳定
- 设计优秀
- 性能卓越
```

除非能够提供实际依据，否则不要使用这种宣传式描述。

README 是技术文档，不是广告。

---

## 3. 环境准备（**新增强化章节，必须显式存在**）

在“快速开始”之前，必须先有明确的“环境准备”章节，让用户知道**在真正运行项目之前需要准备什么**。

环境准备章节至少应包含以下内容，并按顺序组织：

### 3.1 支持的操作系统

明确说明项目在哪些操作系统上可以运行。例如：

- Windows 10 / 11
- macOS 12+
- Linux（Ubuntu 20.04+、Debian 11+ 等）

如果项目只在某个平台测试过，应如实说明：

> 当前项目主要在 Windows 11 上开发和测试，其他平台尚未验证。

**不要声称支持未经测试的平台。**

### 3.2 需要的运行时 / 语言版本

明确说明所需的编程语言或运行时版本。例如：

- Python 3.10 及以上
- Node.js 18 及以上
- JDK 17 及以上
- .NET 6 及以上

如果项目对版本比较敏感，应给出更具体的范围：

> Python 3.10 ~ 3.12（3.13 尚未验证）

### 3.3 需要的系统级工具

如果项目依赖某些系统级工具（而不是语言包管理器安装的库），必须单独列出，并给出**各平台的安装方式**。例如：

- Git
- CMake
- gcc / clang / MSVC
- ffmpeg
- Tesseract OCR
- CUDA / cuDNN

例如：

````markdown
### Windows

1. 安装 Git：https://git-scm.com/download/win
2. 安装 CMake：https://cmake.org/download/

### macOS

```bash
brew install git cmake
```
````

### Linux（Debian / Ubuntu）

```bash
sudo apt update
sudo apt install -y git cmake
```

````

### 3.4 可选依赖

如果某些功能需要额外的依赖，应说明：

- 哪些功能需要它们；
- 如何安装；
- 不安装会有什么影响。

### 3.5 环境准备检查清单

建议在环境准备章节末尾提供一个**检查清单**，让用户可以逐项确认：

```text
[ ] 已安装 Python 3.10+
[ ] 已安装 Git
[ ] 已安装 FFmpeg
[ ] 已确认命令行可以运行 python --version
````

这样用户可以在进入下一步之前，确认自己已经准备就绪。

---

## 4. 一键安装 / 完整依赖安装（**新增强化章节，必须优先提供**）

> 这是本版本最重要的用户友好性改进之一。
>
> **不要只列出几个库让用户自己一个一个敲。** 应当尽可能提供一份**完整、可直接复制粘贴**的依赖安装命令，让用户一次完成环境准备。

### 4.1 优先提供完整的依赖安装命令

对于 Python 项目，应当提供类似：

```bash
pip install -r requirements.txt
```

如果项目没有 `requirements.txt`，应当根据项目实际依赖，提供**完整的一行或一段安装命令**，例如：

```bash
pip install numpy pandas matplotlib scikit-learn opencv-python
```

对于 Node.js 项目：

```bash
npm install
```

或：

```bash
npm install express axios dotenv
```

对于 C++ 项目：

```bash
# 以 vcpkg 为例
vcpkg install fmt spdlog nlohmann-json
```

对于 Rust 项目：

```bash
cargo build
```

对于 Go 项目：

```bash
go mod download
```

**注意：** 上面只是形式示例。实际写 README 时，必须使用项目真实存在的依赖，不能编造。

### 4.2 提供一键安装脚本（如果项目适合）

如果项目的依赖比较多，或者安装步骤比较繁琐，应当提供**一键安装脚本**。

例如：

```bash
# Linux / macOS
bash scripts/install.sh
```

```powershell
# Windows PowerShell
.\scripts\install.ps1
```

如果项目中没有现成脚本，README 中也可以直接给出一段**完整的、可复制粘贴的安装代码块**，让用户一次执行。

例如：

```bash
# 一键安装全部依赖（Python 示例）
python -m venv .venv
source .venv/bin/activate      # Windows 使用 .venv\Scripts\activate
pip install --upgrade pip
pip install -r requirements.txt
```

### 4.3 明确区分“必需依赖”和“可选依赖”

安装章节应当明确：

- **必需依赖**：不安装就无法运行；
- **可选依赖**：只影响部分功能。

例如：

````markdown
### 必需依赖

```bash
pip install -r requirements.txt
```
````

### 可选依赖

如果需要使用 GPU 加速：

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu121
```

### 4.4 提供安装验证命令

安装完成后，应提供一条简单的验证命令，让用户确认安装成功。例如：

```bash
python -c "import numpy; print(numpy.__version__)"
```

或：

```bash
pip list
```

## 5. 快速开始（**强化：最短路径 + 可复制**）

这是用户部分最重要的内容之一。

应该尽可能让用户完成：

> **安装 → 运行 → 得到结果**

快速开始应当满足：

1. **最短路径原则**：只展示最常用、最简单的一种运行方式；
2. **可复制原则**：所有命令都可以直接复制粘贴；
3. **可验证原则**：运行后应给出预期输出或预期结果。

例如：

```bash
git clone <项目地址>
cd <项目目录>
pip install -r requirements.txt
python main.py
```

如果项目不需要安装，应明确说明。

如果存在多种运行方式：

- 优先展示最常用、最简单的一种；
- 其他方式放到后续章节；
- 不要一开始就把所有高级选项堆给新用户。

### 5.1 快速开始的推荐结构

建议快速开始章节按以下结构组织：

```text
第 1 步：获取项目代码
第 2 步：进入项目目录
第 3 步：安装依赖
第 4 步：运行程序
第 5 步：确认结果
```

每一步都应当：

- 给出具体命令；
- 说明该命令的作用；
- 说明执行后应该看到什么。

### 5.2 示例

````markdown
## 快速开始

### 第 1 步：获取项目代码

```bash
git clone https://github.com/xxx/yyy.git
```
````

### 第 2 步：进入项目目录

```bash
cd yyy
```

### 第 3 步：安装依赖

```bash
pip install -r requirements.txt
```

### 第 4 步：运行程序

```bash
python main.py
```

### 第 5 步：确认结果

如果运行成功，终端应输出类似：

```text
程序已启动，正在处理...
处理完成，结果保存在 output/result.txt
```

````

## 6. 安装与环境（**强化：与“环境准备”“一键安装”衔接**）

“安装与环境”章节应当与前面的“环境准备”和“一键安装”章节形成衔接，而不是重复。

可以按以下方式组织：

- 如果“环境准备”已经详细说明了系统要求，这里只需要引用；
- 如果“一键安装”已经给出了完整安装命令，这里可以补充**分步骤安装说明**或**手动安装说明**；
- 如果项目支持多种安装方式（如 pip、conda、源码安装、Docker），应分别说明。

根据实际项目说明：

- 操作系统要求；
- 编程语言版本；
- 必需依赖；
- 可选依赖；
- 安装命令；
- 虚拟环境要求；
- 外部软件；
- 环境变量；
- 特殊系统配置。

如果不同操作系统的安装方式不同，应当分别说明。

例如：

```markdown
### Windows

...

### macOS

...

### Linux

...

````

但是如果三个平台完全一致，则没有必要重复三遍。

**不要列出项目实际上没有使用的依赖。**

## 7. 使用方法

必须基于项目实际功能编写。

如果是命令行程序：

```bash
program [选项] <输入>
```

并解释实际参数：

| 参数    | 说明 | 默认值 |
| ------- | ---- | ------ |
| `--xxx` | xxx  | xxx    |

如果是 GUI：

1. 如何启动；

如果是 Python/C++/Java 等库：

提供最小可运行示例。

### 7.1 使用方法的分层

# 五、开发者部分写作要求

开发者部分是本 README 与普通项目介绍最重要的区别。

## 1. 项目结构

根据实际目录生成项目结构。

| `src/utils/` | 通用工具 |
| `tests/`     | 测试     |
| `main.py`    | 程序入口 |

**不要把每一个无意义的小文件都解释一遍。**

但如果某个看起来普通的文件实际上承担重要职责，则应当说明。

## 2. 技术栈

尽可能使用中文描述。

- Python；
- C++；
- PySide6；
- PyMuPDF；
- CMake；
- Git；

不要为了中文化而强行翻译这些正式技术名称。

如果某项只是开发工具，而不是程序运行时依赖，应当明确区分。

---

## 3. 系统架构

对于存在一定复杂度的项目，需要说明整体架构。

重点回答：

可以使用：

```text
输入
  ↓

  ↓
核心逻辑
  ↓

  ↓
输出
```

不要为了“看起来专业”而强行使用复杂图表。

如果简单文字或目录结构已经足够清楚，就不要额外制造复杂图表。

## 4. 核心执行流程

对于复杂项目，应进一步说明：

- 初始化；

- 异常路径；
- 程序退出流程。

## 5. 核心模块

README 需要解释代码结构和设计，而不是代替源代码。

## 7. 关键设计与实现

对于值得开发者理解的设计，应解释：

- 为什么采用当前实现方案；

- 哪些地方存在技术权衡；

但是必须特别注意：

**不要编造作者没有做过的设计决策。**

如果无法确定作者为什么这么设计，可以客观描述：

> “当前实现采用……”

而不要写成：

除非代码或其他项目资料能够支持这种判断。

# 六、复杂项目的额外要求

如果项目规模较大，应当自动增加 README 深度。

例如项目具有：

- 多个核心模块；
- 多种输入输出；
- GUI + 命令行；
- 数据库；
- 网络服务；
- 插件系统；
- 多线程/异步；
- 复杂配置；
- 多平台支持；
- 编译系统；
- 多个外部依赖；

则不能只写：

> 项目简介 + 安装方法 + 简单目录。

应根据实际情况增加：

- 系统架构；
- 模块关系；
- 数据流；
- 生命周期；
- 配置系统；
- 接口；
- 扩展机制；
- 构建系统；
- 测试体系；
- 部署方式；
- 性能相关注意事项；
- 平台兼容性；
- 已知限制；
- 重要设计取舍。

如果项目规模非常大，可以进一步按照模块拆分开发者文档，但 README 本身仍然应当承担“总入口”的职责。

---

# 七、篇幅控制原则

README **没有固定字数限制**。

应该遵循：

> **最小项目，最小文档；复杂项目，完整文档。**

不要为了“详细”强行写长，也不要因为害怕 README 太长而删除真正有价值的信息。

尤其注意：

### 宁可增加技术信息，也不要增加空泛描述。

一个包含 20 个源文件的项目，README 比一个 100 行脚本长很多是正常的。

一个拥有复杂架构的项目，README 达到数千字甚至更多也是合理的。

但是：

> **README 的目标不是尽可能长，而是让信息密度尽可能高。**

如果某段内容不能帮助：

- 用户使用项目；
- 开发者理解项目；
- 开发者维护项目；
- 开发者扩展项目；

那么就应该考虑删除。

---

# 八、README 中的代码、命令与项目结构

所有代码、命令、路径、参数必须尽量来自实际项目。

代码块应注明语言：

```bash
python main.py
```

```python
from xxx import xxx
```

路径必须与项目实际结构一致。

不要出现：

```text
your_project/
your_file.py
some_command
```

这种仅用于凑格式的占位内容，除非确实需要用户自行替换。

如果确实存在需要用户替换的变量，应明确说明：

```bash
python main.py <你的文件路径>
```

而不是假装这是一个真实文件名。

# 九、版本与兼容性

如果项目能够确定版本信息，应说明：

- 当前版本；
- 支持的语言版本；
- 支持的操作系统；
- 关键依赖版本；
- 已测试的平台；
- 平台之间存在的差异。

如果无法确认，不要自行编造版本号。

如果代码实际上没有进行跨平台测试，也不要写：

> “完全支持 Windows、macOS 和 Linux。”

可以客观描述当前能够确认的信息。

# 十、截图、GIF、示意图与可视化内容

如果项目是：

- GUI；
- 可视化工具；
- 图像处理工具；
- 数据分析工具；
- 具有明显交互界面的应用；

应考虑是否需要加入：

- 截图；
- GIF；
- 架构图；
- 流程图；

但只有在这些内容能够真正帮助用户理解项目时才加入。

不要为了“看起来专业”而加入没有信息价值的图片。

如果当前环境无法获得真实截图，也不要伪造截图。

# 十四、语言与表达风格

README 默认使用**中文**编写。

整体风格要求：

- 专业；
- 清晰；
- 克制；
- 信息密度高；
- 技术准确；
- 易于扫描；
- 不故作高深；
- 不营销化；
- 不写论文腔；
- 不写流水账。

优先使用：

- 中文标题；
- 小标题；
- 表格；
- 列表；
- 代码块；
- 简短段落。

正式技术名称、库名称、命令、API、类名、函数名等可以保留英文。

例如：

> 使用 `PyMuPDF` 处理 PDF 文件。

而不是强行翻译技术名称。

避免连续的大段文字。

---

# 十五、README 的阅读层次

最终 README 应形成明显的阅读层次：

```text
第一层：我第一次看到这个项目
        ↓
        知道它是什么、能干什么

第二层：我想使用它
        ↓
        能快速安装并运行

第三层：我想深入使用
        ↓
        知道参数、配置、输入输出

第四层：我想开发它
        ↓
        理解目录、模块、架构和数据流

第五层：我想维护 / 扩展它
        ↓
        理解设计、测试、构建和扩展方式
```

README 不应该要求普通用户阅读完整篇文档才能开始使用。

同时，开发者也不应该因为 README 过度简略，而必须自行阅读大量源代码才能弄清楚项目的大致结构。

---

# 十六、README 的信息优先级

如果需要在“完整”和“简洁”之间进行取舍，应优先保留以下信息：

### 第一优先级：项目是什么

- 项目用途；
- 核心功能；
- 适用场景。

### 第二优先级：怎么使用

- 环境；
- 安装；
- 快速开始；
- 基本用法；
- 输入输出。

### 第三优先级：怎么理解

- 项目结构；
- 技术栈；
- 架构；
- 核心模块；
- 执行流程。

### 第四优先级：怎么继续开发

- 接口；
- 设计；
- 测试；
- 构建；
- 扩展；
- 部署。

这并不意味着第四优先级内容不重要，而是意味着**如果项目规模很小，不应该为了写满这些内容而强行制造内容。**

---

# 十七、必须区分“事实”和“推测”

这是技术 README 中非常容易出现的问题。

以下内容属于事实：

> 项目使用 PyMuPDF。

如果可以从依赖文件或源代码确认，就可以直接写。

以下属于推测：

> 作者使用 PyMuPDF 是为了提高 PDF 处理性能。

除非项目文档或其他明确资料能够支持，否则不要这样写。

类似地：

不要擅自声称：

- “这是为了性能优化”；
- “这是为了提高安全性”；
- “这是为了方便维护”；
- “作者采用这个结构是因为……”。

如果无法确定原因，可以改成：

> 当前实现使用……

或者：

> 当前代码将……划分为……

**README 应该记录项目，而不是替作者编造项目设计思想。**

---

# 十八、已有 README 的处理方式

如果当前项目已经存在 README：

**不要无视原 README，直接从零重新生成。**

应当：

1. 阅读原 README；
2. 理解原作者已经提供的信息；
3. 与当前代码和项目结构进行核对；
4. 保留仍然准确、有价值的内容；
5. 修正过时内容；
6. 补充缺失内容；
7. 重组结构；
8. 删除重复、空泛和错误内容。

最终目标是得到一份更好的 README，而不是简单地“覆盖旧 README”。

---

# 十九、信息缺失时的处理方式

如果 README 中应该出现某项信息，但当前项目无法确认：

### 可以确认

直接写。

### 可以从代码合理推断，但不是绝对确定

使用客观、保守的表达。

### 完全无法确认

不要编造。

可以：

- 省略；
- 标记“待补充”；
- 或在文档适当位置说明“当前项目未提供相关信息”。

**不要为了让 README 看起来完整而制造事实。**
