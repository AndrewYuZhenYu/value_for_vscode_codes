# README 编写规范

你需要为当前项目编写一份**专业、完整、准确、可长期维护、对用户真正友好**的 `README.md`。

这不是一份简单的项目简介，也不是机械套用 GitHub README 模板。

你必须**先真正理解当前项目**，再根据项目实际规模、功能、技术栈、代码结构、使用场景和开发复杂度，自主决定 README 的结构、深度和篇幅。

README 的核心目标是：

> **让普通用户能够最快理解“这是什么、能做什么、需要什么、怎么安装、怎么运行、运行成功后会得到什么、遇到问题怎么办”；让开发者能够充分理解“它是怎么实现的、各部分如何协作、为什么这样设计、如何继续开发和维护”。**

README 应当是一份真正服务于项目本身的文档，而不是为了满足某种固定格式而存在的模板。

---

# 一、最重要的总体原则

## 1. 必须以项目实际内容为依据

在开始编写 README 之前，必须尽可能充分地检查和理解当前项目。

根据项目情况，应当检查但不限于：

- 项目源代码；
- 项目完整目录结构；
- 程序入口；
- 配置文件；
- `requirements.txt`、`pyproject.toml`、`package.json`、`CMakeLists.txt` 等依赖或构建文件；
- 示例代码；
- 命令行参数；
- GUI 界面；
- API 接口；
- 数据文件；
- 测试代码；
- 脚本；
- 构建方式；
- 打包方式；
- 部署方式；
- LICENSE；
- 已有文档；
- 注释；
- 已有 README；
- 项目中的版本信息；
- 项目实际使用的第三方库；
- 项目实际支持的平台；
- 项目实际产生的输入和输出。

**不要根据项目名称、文件名称或少量代码猜测项目功能。**

README 中出现的：

- 功能；
- 命令；
- 参数；
- 文件名；
- 目录；
- API；
- 依赖；
- 运行方式；
- 架构关系；
- 技术细节；

都应尽可能能够从项目实际内容中得到依据。

如果某项信息无法确认：

- 不要擅自编造；
- 不要为了让 README 看起来完整而猜测；
- 可以直接省略；
- 如果确实有必要，可以明确标记为“待补充”或“当前项目未提供相关信息”。

**准确性永远优先于完整性。**

---

## 2. 绝对不要机械套用模板

README **不是固定模板填空题**。

下面列出的章节只是为了提醒你：

> **一个优秀的 README 通常可能需要考虑哪些方面。**

它们**不是强制目录，更不是固定顺序**。

你必须根据当前项目自行判断。

例如：

- 一个几十行的小工具，不需要写成几十页；
- 一个几百行的小型个人工具，应重点说明用途、安装和使用方式；
- 一个几千行的个人项目，需要适当说明核心功能、结构和实现；
- 一个几十个源文件、多个模块组成的项目，应提供较完整的架构和开发者文档；
- 一个库/API 项目，应重点说明安装、接口和调用方式；
- 一个命令行工具，应重点说明命令、参数、输入和输出；
- 一个 GUI 项目，应重点说明界面、操作流程、配置和结果；
- 一个数据处理项目，应重点说明输入、处理流程、输出格式；
- 一个网络服务，应重点说明接口、通信流程、部署和配置；
- 一个课程/学习项目，可以适当说明设计目的和学习内容，但不要把 README 写成课程实验报告；
- 一个内部个人工具，可能根本不需要贡献指南、路线图等章节。

**如果你认为当前项目不适合某个章节，可以直接不写。**

反过来，如果项目中存在本规范没有明确列出的重要内容，也应该主动增加相应章节。

**你按照自己的判断生成的结构，只要最符合当前项目实际情况，就是最好的结构。**

---

# 二、详细不等于废话多

README 可以详细，而且对于复杂项目，应该足够详细。

但是绝对不要通过以下方式制造所谓的“详细”：

- 重复描述同一个功能；
- 使用大量空泛形容词；
- 反复解释显而易见的内容；
- 把代码逐行翻译成自然语言；
- 把所有函数都逐个解释一遍；
- 大段介绍与项目实际使用无关的背景知识；
- 使用大量“本项目具有……”“通过……可以……”等没有实际信息量的句子；
- 为了看起来专业而加入没有实际意义的章节；
- 为了满足固定字数而重复内容；
- 把项目中很简单的逻辑故意写得复杂。

应该优先增加**信息密度**。

例如：

> 一个真实参数、一个实际命令、一个准确的目录说明、一个真实输入输出示例、一个模块之间的依赖关系、一个关键设计原因，都比一大段空泛介绍更有价值。

**宁可增加有价值的技术信息，也不要增加没有信息量的文字。**

---

# 三、README 的核心读者

README 至少需要同时服务两类主要读者。

## 1. 普通用户

普通用户最关心：

1. 这是什么？
2. 能解决什么问题？
3. 有什么主要功能？
4. 需要什么环境？
5. 安装什么？
6. 如何安装？
7. 如何运行？
8. 最简单的使用方法是什么？
9. 输入什么？
10. 输出什么？
11. 如果运行失败怎么办？

因此用户部分应该：

- 简洁；
- 直接；
- 可操作；
- 信息密度高；
- 尽量少讲内部实现；
- 避免让用户阅读大量开发者内容才能开始使用。

**普通用户应该能够在很短时间内完成第一次运行。**

---

## 2. 开发者

开发者最关心：

1. 项目如何组织？
2. 使用了什么技术？
3. 核心模块是什么？
4. 模块之间如何协作？
5. 程序从哪里开始执行？
6. 程序主要执行流程是什么？
7. 数据如何在模块之间流动？
8. 核心逻辑在哪里？
9. 关键设计为什么这样实现？
10. 如何增加功能？
11. 如何修改现有功能？
12. 如何替换某个模块？
13. 如何构建？
14. 如何测试？
15. 如何发布或部署？
16. 当前有什么限制？

因此开发者部分可以明显更加详细。

对于复杂项目，应根据实际情况提供：

- 项目结构；
- 技术栈；
- 系统架构；
- 模块说明；
- 执行流程；
- 数据流；
- 核心类和函数；
- 关键设计；
- 配置机制；
- 异常处理；
- 测试体系；
- 构建方式；
- 发布方式；
- 扩展方式；
- 已知限制。

---

# 四、用户友好性：README 必须提供完整的操作路径

这是本规范的重要增强内容。

README 不应该只是“信息的集合”，而应该让用户能够沿着文档一步一步完成：

```text
认识项目
    ↓
确认环境要求
    ↓
准备运行环境
    ↓
安装全部必要依赖
    ↓
准备必要资源
    ↓
完成配置
    ↓
第一次运行
    ↓
确认运行成功
    ↓
正式使用
    ↓
遇到问题时排查
```

**用户友好型 README 的核心不是写更多，而是让“下一步做什么”始终明确。**

不要假设用户知道下一步该做什么。

README 应主动告诉用户：

- 现在应该做什么；
- 在什么目录执行；
- 执行什么命令；
- 哪些内容需要替换；
- 执行成功后应该看到什么；
- 下一步应该做什么。

---

## 1. 必须明确区分用户操作阶段

对于存在环境配置的项目，用户部分应尽量形成以下逻辑：

### 阶段一：认识项目

回答：

- 这是什么；
- 解决什么问题；
- 主要功能是什么；
- 适合什么场景。

### 阶段二：环境准备

回答：

- 需要什么操作系统；
- 需要什么语言版本；
- 需要什么运行时；
- 是否需要编译器；
- 是否需要 Git；
- 是否需要 CUDA；
- 是否需要数据库；
- 是否需要外部软件；
- 是否需要模型、数据集或其他资源。

### 阶段三：安装

回答：

- 需要安装哪些依赖；
- 是否存在依赖文件；
- 是否需要创建虚拟环境；
- 应该执行什么完整命令。

### 阶段四：配置

回答：

- 是否需要配置文件；
- 是否需要环境变量；
- 是否需要 API Key；
- 是否需要修改路径；
- 是否需要准备模型；
- 哪些配置是必须的。

### 阶段五：第一次运行

回答：

- 从哪个目录运行；
- 使用什么命令；
- 是否需要参数；
- 正常运行应该出现什么；
- 输出保存在哪里。

### 阶段六：正式使用

第一次运行成功后，再介绍：

- 常用参数；
- 常用功能；
- 不同运行模式；
- 高级配置；
- 批量处理；
- 自定义功能。

### 阶段七：故障排查

如果项目确实存在常见问题，应告诉用户：

- 如何判断问题；
- 可能原因；
- 解决方法；
- 解决后重新执行什么。

---

# 五、快速开始必须是真正的“最短成功路径”

快速开始是用户部分最重要的内容之一。

它的目标不是展示 README 有多专业，而是：

> **让一个第一次接触项目的人，以尽可能少的步骤完成第一次成功运行。**

理想情况下形成：

```text
获取项目
    ↓
准备环境
    ↓
安装依赖
    ↓
准备必要文件
    ↓
运行
    ↓
查看结果
```

例如：

```markdown
## 快速开始

### 第 1 步：获取项目

...

### 第 2 步：安装环境

...

### 第 3 步：准备必要文件

...

### 第 4 步：运行

...

### 第 5 步：确认结果

...
```

如果某一步在当前项目中不存在，就不要为了形式强行增加。

---

## 1. 快速开始必须说明“成功标志”

不要只告诉用户：

```bash
python main.py
```

还应该尽可能说明：

- 正常情况下终端会出现什么；
- 会生成什么文件；
- 文件保存在哪里；
- GUI 会出现什么界面；
- 什么现象代表运行成功。

例如：

```text
运行完成后，项目目录下会生成：

output/
└── result.pdf
```

这样用户才能判断：

> **程序到底是真的成功了，还是只是没有报错？**

---

# 六、环境准备必须完整

“环境准备”不能只列出几个软件名称。

应该根据实际项目回答：

- 操作系统；
- 编程语言及版本；
- 编译器；
- 包管理器；
- 运行时；
- 外部软件；
- GPU / CUDA；
- 数据库；
- 浏览器或驱动；
- 其他系统依赖。

同时必须区分：

> **运行项目需要什么**

和：

> **开发项目需要什么**

两者不要混在一起。

例如某个 IDE 只是开发者使用的工具，而普通用户运行程序并不需要，就不应该把它写成运行前置条件。

---

# 七、依赖安装必须尽可能降低用户操作成本

这是用户友好性的重要增强。

如果项目存在完整的依赖文件，应优先提供**直接安装全部依赖**的方式。

例如 Python 项目存在 `requirements.txt`：

```bash
python -m pip install -r requirements.txt
```

而不是只写：

```text
需要安装：
- PyMuPDF
- EasyOCR
- ultralytics
- pypdf
```

然后让用户自己一个一个安装。

---

## 1. 没有依赖文件时，应尽可能提供完整安装命令

如果项目没有 `requirements.txt`，但能够从项目实际代码和配置中确认依赖，应尽量给出：

```bash
python -m pip install package-a package-b package-c
```

而不是：

```text
请安装 package-a。
请安装 package-b。
请安装 package-c。
```

**能合并成一条完整命令，就优先提供一条完整命令。**

但必须遵守：

> **只安装项目实际需要的依赖。**

不能为了“方便”把可能有用、曾经使用过或者猜测可能需要的库全部加入。

---

## 2. 优先使用项目已有的标准依赖文件

根据项目实际情况，应优先识别：

- `requirements.txt`
- `pyproject.toml`
- `poetry.lock`
- `package.json`
- `package-lock.json`
- `CMakeLists.txt`
- `pom.xml`
- `build.gradle`
- 其他实际依赖或构建文件

这些文件比人工猜测依赖更加可靠。

---

## 3. 虚拟环境

如果项目适合使用 Python 虚拟环境，应在 README 中提供完整流程，而不是只写“建议使用虚拟环境”。

例如：

```bash
python -m venv .venv
```

然后根据实际平台给出激活方法。

激活后：

```bash
python -m pip install -r requirements.txt
```

如果项目不需要虚拟环境，则不必为了“规范”强行增加。

---

# 八、一键安装脚本

如果项目实际存在：

- `setup.bat`
- `setup.ps1`
- `setup.sh`
- `install.py`
- 其他安装脚本

应明确告诉用户：

- 脚本名称；
- 使用平台；
- 如何执行；
- 脚本完成了什么；
- 执行完成后的下一步是什么。

例如：

```text
Windows 用户可以运行项目提供的 setup.bat。

执行完成后，再运行：
...
```

如果项目不存在安装脚本：

**绝对不能假装项目存在一键安装脚本。**

用户友好不等于编造功能。

---

# 九、其他语言的环境安装

对于 Node.js、C/C++、Java 等项目，也应遵循相同原则。

例如 Node.js 项目存在 `package.json`，应根据实际项目使用的包管理方式提供：

```bash
npm install
```

或者项目实际采用的其他方式。

C/C++ 项目如果实际使用 CMake，可以根据项目实际构建方式提供相应命令。

Java 项目如果存在 `pom.xml` 或 `build.gradle`，应根据实际构建系统说明。

**不要机械套用某一种语言的安装模板。**

---

# 十、明确用户需要自行准备的资源

有些项目安装完依赖仍然不能直接运行。

例如需要：

- 模型文件；
- 权重文件；
- 数据集；
- 输入文件；
- API Key；
- `.env`；
- 数据库；
- 外部程序；
- 特定目录；
- CUDA；
- 浏览器驱动。

此时必须明确说明：

```text
运行前还需要准备：

1. xxx
2. xxx
3. xxx
```

并尽可能说明：

- 从哪里获得；
- 文件名是什么；
- 放在哪里；
- 是否必须；
- 缺少后会发生什么。

**不要让用户运行到一半才发现还缺少关键资源。**

---

# 十一、环境安装与项目配置必须形成连续流程

不要把相关信息分散到 README 各处，让用户自己拼接。

如果项目实际流程是：

```text
安装 Python
    ↓
创建虚拟环境
    ↓
安装依赖
    ↓
下载模型
    ↓
修改配置文件
    ↓
运行程序
```

README 就应该尽量按照这个顺序组织。

用户不应该读完“安装”后才在十几页之后发现：

> 原来还需要下载一个模型。

---

# 十二、不同操作系统的说明

如果 Windows、macOS、Linux 的操作完全一致，不需要重复三遍。

如果存在差异，应明确区分：

```markdown
### Windows

...

### macOS / Linux

...
```

尤其注意：

- 路径；
- shell 命令；
- 虚拟环境激活方式；
- 编译器；
- 系统依赖；
- 权限；
- 可执行文件；
- GPU / CUDA；
- 外部软件。

不要只写：

> 支持 Windows、macOS 和 Linux。

却不给出真正需要的差异。

---

# 十三、使用方法

必须基于项目实际功能编写。

如果是命令行程序：

```bash
program [选项] <输入>
```

并解释真实参数：

| 参数    | 说明 | 默认值 |
| ------- | ---- | ------ |
| `--xxx` | xxx  | xxx    |

如果是 GUI：

应说明：

1. 如何启动；
2. 主界面有哪些功能；
3. 用户需要进行什么操作；
4. 每个重要按钮或区域的作用；
5. 程序产生什么结果；
6. 结果保存在哪里。

如果是 Python / C++ / Java 等库：

提供最小可运行示例。

---

# 十四、输入与输出

如果项目具有明确的输入和输出，应当单独说明。

重点回答：

- 支持什么输入；
- 输入格式；
- 必要字段；
- 输出格式；
- 输出位置；
- 文件命名规则；
- 特殊情况。

例如：

```text
输入文件
    ↓
读取
    ↓
处理
    ↓
输出文件
```

对于数据处理、转换、分析类程序，这一部分尤其重要。

---

# 十五、真实使用示例

如果项目适合展示示例，应提供：

> **真实、可复制、与当前代码一致的示例。**

例如：

```bash
python main.py example.pdf
```

然后说明实际输出。

示例中的：

- 命令；
- 参数；
- 文件；
- 路径；
- 输出；

都必须能够从项目实际情况得到依据。

**绝对不要编造不存在的命令、参数、文件或输出结果。**

---

# 十六、配置说明

如果项目存在：

- 配置文件；
- 环境变量；
- 命令行参数；
- 用户设置；
- 配置目录；

应集中说明。

例如：

| 配置项 | 作用 | 默认值 | 是否必须 |
| ------ | ---- | ------ | -------- |
| `XXX`  | ...  | ...    | 是       |

如果配置文件较复杂，可以进一步解释配置结构。

# 十七、常见问题与故障排查

只记录真正可能遇到的问题。

例如：

```markdown
### xxx 错误

原因：

...

解决：

...
```

如果能够从代码判断错误来源，应尽可能说明具体原因。

不要为了让 README 看起来“完整”而制造不存在的问题。

---

# 十八、开发者部分

开发者部分是 README 与普通项目介绍最重要的区别。

对于复杂项目，这一部分应该明显比用户部分更加深入。

---

## 1. 项目结构

根据实际目录生成项目结构。

例如：

```text
project/
├── src/
│   ├── core/
│   ├── utils/
│   └── ...
├── tests/
├── docs/
├── examples/
├── README.md
├── requirements.txt
└── LICENSE
```

然后解释重要目录和文件。

不要把每一个无意义的小文件都解释一遍。

但如果某个看起来普通的文件实际上承担重要职责，则应当说明。

---

## 2. 技术栈

明确列出项目实际使用的技术。

例如：

```text
- 编程语言：Python
- GUI：PySide6
- PDF 处理：PyMuPDF
- 构建工具：...
- 测试框架：...
```

正式技术名称可以保留英文。

如果某项只是开发工具，而不是程序运行时依赖，应明确区分。

---

## 3. 系统架构

对于存在一定复杂度的项目，需要说明整体架构。

重点回答：

> **程序由哪些核心部分组成？这些部分之间如何协作？**

优先使用普通 Markdown、列表、表格以及纯文本箭头。

例如：

```text
输入
  ↓
解析
  ↓
核心逻辑
  ↓
处理
  ↓
输出
```

**禁止为了“看起来专业”使用 Mermaid、PlantUML、Graphviz DOT 等需要特殊渲染器的图表语言。**

如果纯文本已经能够表达清楚，就使用纯文本。

只有在确实需要图形化展示，并且项目已经存在真实图片资源时，才考虑使用图片。

---

## 4. 核心执行流程

说明程序从启动到结束的大致过程。

例如：

```text
程序启动
→ 加载配置
→ 验证输入
→ 读取数据
→ 核心处理
→ 生成结果
→ 保存或展示结果
```

对于复杂项目，应进一步说明：

- 初始化；
- 关键分支；
- 模块调用顺序；
- 异常路径；
- 程序退出流程。

---

## 5. 核心模块

逐个解释真正重要的模块。

每个模块至少可以说明：

- 职责；
- 输入；
- 输出；
- 与其他模块的关系；
- 关键实现方式；
- 是否可以独立替换；
- 修改时需要注意什么。

**不要逐行解释代码。**

README 需要解释代码结构和设计，而不是代替源代码。

---

## 6. 核心数据流

如果项目存在明显的数据流，应当解释：

```text
输入数据
↓
解析
↓
内部数据结构
↓
核心处理
↓
结果对象
↓
输出文件
```

重点说明：

- 数据从哪里产生；
- 使用什么结构保存；
- 在哪里转换；
- 哪个模块处理；
- 最终如何输出。

---

## 7. 关键设计与实现

对于值得开发者理解的设计，应解释：

- 当前实现采用什么方案；
- 为什么使用某个库；
- 为什么采用某种数据结构；
- 为什么代码拆分成当前模块；
- 哪些设计涉及兼容性；
- 哪些设计涉及可维护性；
- 哪些地方存在技术权衡；
- 哪些实现存在特殊处理。

但是必须特别注意：

**不要编造作者没有做过的设计决策。**

如果无法确定原因，可以客观描述：

> 当前实现采用……

而不要写：

> 作者为了提高性能，所以……

除非代码或其他项目资料能够支持这种判断。

# 十九、接口、类与函数

### `parse_document(path)`

**参数**

- `path`：输入文件路径。

**返回值**

解析后的文档对象。

**异常**

- 类的职责；
- 成员；
- 构造方式；
- 重要方法；
- 输入输出；
- 使用关系。

但不要把每个简单 getter/setter 都写成长篇说明。

**说明深度应与接口的重要程度匹配。**

# 二十、错误处理

如果项目存在明确的异常处理机制，应说明：

- 错误类型；
- 错误产生位置；
- 错误传播方式；
- 用户看到什么；
- 开发者如何定位；
- 日志在哪里；
- 是否会自动恢复。

# 二十一、测试

如果项目存在测试，应说明：

- 使用什么测试框架；
- 测试目录在哪里；
- 如何运行；
- 测试覆盖哪些核心功能；
- 是否存在测试数据；
- 是否有特殊测试环境要求。

例如：

```bash
pytest
```

如果没有测试：

**不要虚构测试体系。**

可以客观说明：

> 当前项目暂无自动化测试。

如果只有部分手工测试，也应如实说明。

# 二十二、开发环境

如果项目具有明确的开发环境，应说明：

- 编程语言版本；
- IDE；
- 编译器；
- 构建工具；
- 包管理器；
- 必要 SDK；
- 操作系统；
- 开发依赖。

> **参与开发所需环境**

# 二十三、构建、打包、发布与部署

如果项目存在编译、构建、打包、发布或部署流程，应根据实际情况说明：

- 开发环境；
- 构建命令；
- 构建过程；
- 输出产物；
- 打包方式；
- 发布流程；
- 部署方法；
- 平台差异。

不要因为某个项目没有发布流程，就强行创建“发布”章节。

---

# 二十四、扩展与二次开发

对于具有持续开发价值的项目，应说明：

> **如果开发者想增加一个新功能，应该从哪里开始？**

例如：

```text
新增处理器
→ 创建新模块
→ 实现统一接口
→ 注册到对应模块
→ 添加测试
→ 更新配置
```

如果项目使用插件机制、注册表、工厂模式等，也应该根据实际实现说明。

# 二十五、复杂项目的额外要求

如果项目具有：

- 多个核心模块；
- 多种输入输出；
- GUI + 命令行；
- 数据库；
- 网络服务；
- 插件系统；
- 多线程 / 异步；
- 复杂配置；
- 多平台支持；
- 编译系统；
- 多个外部依赖；

则不能只写：

> 项目简介 + 安装方法 + 简单目录。

应根据实际情况增加：

- 系统架构；
- 模块关系；
- 数据流；
- 生命周期；
- 配置系统；
- 接口；
- 扩展机制；
- 构建系统；
- 测试体系；
- 部署方式；
- 性能相关注意事项；
- 平台兼容性；
- 已知限制；
- 重要设计取舍。

如果项目规模非常大，可以进一步按照模块拆分开发者文档，但 README 本身仍然应当承担“总入口”的职责。

---

# 二十六、篇幅控制

README **没有固定字数限制**。

遵循：

> **最小项目，最小文档；复杂项目，完整文档。**

不要为了“详细”强行写长，也不要因为害怕 README 太长而删除真正有价值的信息。

尤其注意：

> **宁可增加技术信息，也不要增加空泛描述。**

一个包含 20 个源文件的项目，README 比一个 100 行脚本长很多是正常的。

一个拥有复杂架构的项目，README 达到数千字甚至更多也是合理的。

但是：

> **README 的目标不是尽可能长，而是让信息密度尽可能高。**

---

# 二十七、README 中的代码、命令与项目结构

所有代码、命令、路径、参数必须尽量来自实际项目。

代码块应注明语言：

```bash
python main.py
```

```python
from xxx import xxx
```

路径必须与项目实际结构一致。

不要出现：

```text
your_project/
your_file.py
some_command
```

这种仅用于凑格式的占位内容，除非确实需要用户自行替换。

如果确实存在需要用户替换的变量，应明确说明：

```bash
python main.py <你的文件路径>
```

而不是假装这是一个真实文件名。

# 二十八、版本与兼容性

如果项目能够确定版本信息，应说明：

- 当前版本；
- 支持的语言版本；
- 支持的操作系统；
- 关键依赖版本；
- 已测试的平台；
- 平台之间存在的差异。

如果无法确认，不要自行编造版本号。

如果代码实际上没有进行跨平台测试，也不要写：

> 完全支持 Windows、macOS 和 Linux。

应客观描述当前能够确认的信息。

# 二十九、截图、图片与可视化内容

如果项目是：

- GUI；
- 可视化工具；
- 图像处理工具；
- 数据分析工具；
- 具有明显交互界面的应用；

应考虑是否需要加入：

- 截图；
- GIF；
- 架构图；
- 流程图；
- 输出示例。

但只有在这些内容能够真正帮助用户理解项目时才加入。

不要为了“看起来专业”而加入没有信息价值的图片。

如果当前环境无法获得真实截图，也不要伪造截图。

# 三十、许可证

这是固定要求。

如果项目按照本规范生成 README，**License 一律采用以下声明，不得自行改写、扩展或替换为其他许可证表述：**

## License

本项目代码仅供学习、研究与个人使用。未经作者许可，禁止将本项目用于商业用途、直接复制后重新发布，或以本项目及其衍生代码作为独立项目进行再发布。

如果项目中已经存在明确的 LICENSE 文件，应结合项目实际情况处理，但不得擅自把其他许可证改写成上述声明。

**不要自行声称项目采用 MIT、Apache、GPL 等许可证，除非项目实际存在对应许可证。**

---

# 三十一、开发路线

只有当项目确实存在未来计划时才写。

不要虚构开发计划。

如果项目已经稳定，或者作者没有明确的未来计划，可以不写这一部分。

如果项目确实存在路线图，应当只记录能够从项目资料中确认的内容。

---

# 三十二、参与开发

如果项目是个人小工具：

不需要为了套模板强行加入复杂的贡献指南。

如果项目具有多人协作或开源属性，则可以说明：

- Issue；
- Pull Request；
- 开发规范；
- 测试要求；
- Commit 规范；
- 分支策略；
- 代码风格；
- 提交要求。

所有内容以项目实际情况为准。

---

# 三十三、语言与表达风格

README 默认使用**中文**编写。

整体风格要求：

- 专业；
- 清晰；
- 克制；
- 信息密度高；
- 技术准确；
- 易于扫描；
- 不故作高深；
- 不营销化；
- 不写论文腔；
- 不写流水账。

优先使用：

- 中文标题；
- 小标题；
- 表格；
- 列表；
- 代码块；
- 简短段落。

正式技术名称、库名称、命令、API、类名、函数名等可以保留英文。

例如：

> 使用 `PyMuPDF` 处理 PDF 文件。

而不是强行翻译技术名称。

---

# 三十四、README 的阅读层次

最终 README 应形成明显的阅读层次：

```text
第一层：我第一次看到这个项目
        ↓
        知道它是什么、能干什么

第二层：我想使用它
        ↓
        能快速准备环境、安装并运行

第三层：我想深入使用
        ↓
        知道参数、配置、输入输出

第四层：我想开发它
        ↓
        理解目录、模块、架构和数据流

第五层：我想维护 / 扩展它
        ↓
        理解设计、测试、构建和扩展方式
```

README 不应该要求普通用户阅读完整篇文档才能开始使用。

同时，开发者也不应该因为 README 过度简略，而必须自行阅读大量源代码才能弄清楚项目的大致结构。

---

# 三十五、README 的信息优先级

如果需要在“完整”和“简洁”之间进行取舍，应优先保留以下信息。

## 第一优先级：项目是什么

- 项目用途；
- 核心功能；
- 适用场景。

## 第二优先级：怎么使用

- 环境；
- 安装；
- 快速开始；
- 基本用法；
- 输入输出。

## 第三优先级：怎么理解

- 项目结构；
- 技术栈；
- 架构；
- 核心模块；
- 执行流程。

## 第四优先级：怎么继续开发

- 接口；
- 设计；
- 测试；
- 构建；
- 扩展；
- 部署。

这并不意味着第四优先级内容不重要，而是意味着：

**如果项目规模很小，不应该为了写满这些内容而强行制造内容。**

---

# 三十六、必须区分“事实”和“推测”

这是技术 README 中非常容易出现的问题。

以下内容属于事实：

> 项目使用 PyMuPDF。

如果可以从依赖文件或源代码确认，就可以直接写。

以下属于推测：

> 作者使用 PyMuPDF 是为了提高 PDF 处理性能。

除非项目文档或其他明确资料能够支持，否则不要这样写。

类似地，不要擅自声称：

- “这是为了性能优化”；
- “这是为了提高安全性”；
- “这是为了方便维护”；
- “作者采用这个结构是因为……”。

如果无法确定原因，可以改成：

> 当前实现使用……

或者：

> 当前代码将……划分为……

**README 应该记录项目，而不是替作者编造项目设计思想。**

---

# 三十七、已有 README 的处理方式

如果当前项目已经存在 README：

**不要无视原 README，直接从零重新生成。**

应当：

1. 阅读原 README；
2. 理解原作者已经提供的信息；
3. 与当前代码和项目结构进行核对；
4. 保留仍然准确、有价值的内容；
5. 修正过时内容；
6. 补充缺失内容；
7. 重组结构；
8. 删除重复、空泛和错误内容。

最终目标是得到一份更好的 README，而不是简单地“覆盖旧 README”。

---

# 三十八、信息缺失时的处理方式

如果 README 中应该出现某项信息，但当前项目无法确认：

## 可以确认

直接写。

## 可以从代码合理推断，但不是绝对确定

使用客观、保守的表达。

## 完全无法确认

不要编造。

可以：

- 省略；
- 标记“待补充”；
- 或在文档适当位置说明“当前项目未提供相关信息”。

**不要为了让 README 看起来完整而制造事实。**

---

# 三十九、流程图、架构图与特殊标记语言

README 中如果需要表达：

- 程序执行流程；
- 数据流；
- 模块调用关系；
- 系统架构；
- 文件处理流程；
- 用户操作流程；

**优先使用纯 Markdown 文本、列表以及 ASCII 风格的文字和箭头表达。**

例如：

```text
原始 PDF
  ↓
逐页读取
  ↓
图像处理
  ↓
目标检测
  ↓
文字识别
  ↓
层级修复
  ↓
生成书签
  ↓
输出 PDF
```

或者：

```text
输入文件 → 文件解析 → 数据处理 → 结果生成 → 输出文件
```

这种形式具有更好的：

- 跨平台兼容性；
- GitHub / GitLab / 本地 Markdown 编辑器兼容性；
- 可读性；
- 可复制性；
- 长期维护性。

**禁止使用 Mermaid、PlantUML、Graphviz DOT 等需要特殊渲染器或额外支持的图表语言。**

尤其不要为了让 README “看起来更专业”而强行加入特殊图表语法。

如果使用纯文本已经能够清晰表达关系，就应当优先使用纯文本。

只有当项目实际复杂到纯文本难以准确表达，并且确实需要图形化展示时，才考虑使用真实图片或项目已有的图表资源。

**不要为了图表而引入额外的文档语法依赖。**

---

# 四十、最终检查

完成 README 后，在输出之前进行一次完整检查。

## 内容准确性

- [ ] 所有功能都确实存在
- [ ] 所有命令都与项目一致
- [ ] 所有路径都正确
- [ ] 所有参数都真实存在
- [ ] 所有依赖都经过项目确认
- [ ] 没有虚构 API
- [ ] 没有虚构测试
- [ ] 没有虚构开发路线
- [ ] 没有虚构设计动机
- [ ] 没有把推测写成事实
- [ ] 没有把示例写成不存在的实际功能

## 用户体验

- [ ] 开头能够快速理解项目
- [ ] 用户能够明确知道运行前需要准备什么
- [ ] 用户能够明确知道需要安装什么
- [ ] 依赖安装步骤完整
- [ ] 如果存在依赖文件，已经优先提供直接安装方式
- [ ] 如果不存在依赖文件但能够确认依赖，已经尽可能提供完整安装命令

# 四十一、最终要求

请把这次任务理解为：

> **为这个项目制作一份真正可以放进 GitHub / GitLab 项目根目录、供用户和开发者长期使用的正式 README。**

不要把任务理解为：

> “按照固定模板生成一篇 README。”

更不要因为本规范列出了很多章节，就认为这些章节全部必须出现。

**规范提供的是判断标准，而不是固定答案。**

最终文档应该做到：

**用户看前面很短的一部分，就能理解项目是什么、有什么用，并开始准备和使用；**

**用户继续阅读，可以获得完整的环境准备、依赖安装、配置、运行、输入输出和故障排查信息；**

**开发者继续往下阅读，可以逐步理解项目结构、技术栈、架构、模块、数据流、实现方式和维护方法；**

**项目越复杂，开发者部分越详细；项目越简单，则保持克制；**

**信息宁可完整，也不能敷衍；但是绝不通过重复、套话和无意义章节制造所谓的“详细”。**

最重要的是：

> **先理解项目，再决定怎么写 README。**

> **不要先决定 README 应该长什么样，再强行把项目塞进模板。**

如果当前项目已经存在 README，应当在充分理解原 README 后进行**重构、补充和改进**，而不是无视已有内容直接覆盖。

如果项目中存在明显缺失但无法从代码确认的信息，应明确指出缺失项，而不是自行编造。

**最终只输出完整的 `README.md` 内容。**

不要输出分析过程。

不要解释你准备如何写。

不要先给出大纲后等待确认。

不要告诉用户“下面我将……”。

**直接完成 README。**
