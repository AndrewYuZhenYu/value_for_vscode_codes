# README 编写规范（整合精简版）

你需要为当前项目编写一份**专业、完整、准确、可长期维护、对用户真正友好**的 `README.md`。

这不是简单项目简介，也不是机械套用 GitHub 模板。你必须**先真正理解当前项目**，再根据项目实际规模、功能、技术栈、代码结构、使用场景和开发复杂度，自主决定 README 的结构、深度和篇幅。

README 的核心目标：

> **让普通用户最快理解“这是什么、能做什么、需要什么、怎么安装、怎么运行、成功后得到什么、出错怎么办”；让开发者充分理解“怎么实现、如何协作、为什么这样设计、如何继续开发维护”。**

规范提供判断标准，不是固定答案。

---

# 一、总体原则

## 1. 必须以项目实际内容为依据

编写前应检查但不限于：

- 源代码、目录结构、程序入口
- 配置文件、依赖文件（`requirements.txt`、`package.json`、`pyproject.toml`、`CMakeLists.txt`、`pom.xml` 等）
- 示例、命令行参数、GUI、API
- 数据文件、测试、脚本
- 构建 / 打包 / 部署方式
- LICENSE、已有文档、注释、已有 README
- 版本信息、第三方库、支持平台、输入输出

**不要根据项目名、文件名或少量代码猜测功能。**

无法确认的信息：

- 不要编造
- 可以省略
- 必要时标注“待补充”或“当前项目未提供相关信息”

**准确性永远优先于完整性。**

---

## 2. 不要机械套模板

README 不是填空题。下面所有章节只是可选参考，不是强制目录，也不是固定顺序。

项目越简单，文档越克制；项目越复杂，开发者部分越详细。

- 几十行小工具：用途 + 安装 + 使用即可
- 几百行个人工具：重点说明用途、安装、使用
- 几千行个人项目：补充核心功能、结构、实现
- 多模块项目：提供较完整架构和开发者文档
- 库 / API：重点说明安装、接口、调用
- CLI：重点说明命令、参数、输入输出
- GUI：重点说明界面、操作流程、配置、结果
- 数据处理：重点说明输入、处理流程、输出格式
- 网络服务：重点说明接口、通信、部署、配置
- 个人小工具：不必强加贡献指南、路线图

**不适合的章节直接不写。项目里有重要内容但规范没列出的，主动增加。**

---

## 3. 详细不等于废话多

不要通过以下方式制造“详细”：

- 重复描述同一功能
- 大量空泛形容词
- 逐行翻译代码
- 逐个解释所有函数
- 大段无关背景
- “本项目具有……”“通过……可以……”等无信息量句子
- 为凑字数重复内容
- 把简单逻辑写复杂

优先增加**信息密度**：一个真实参数、一条实际命令、一个准确目录说明、一个真实输入输出示例、一个模块依赖关系，都比大段空泛介绍有价值。

**宁可增加有价值的技术信息，也不要增加没有信息量的文字。**

---

## 4. 必须区分“事实”和“推测”

事实（可从依赖文件或源码确认）：

> 项目使用 PyMuPDF。

推测（除非有明确资料支持，否则不要写）：

> 作者使用 PyMuPDF 是为了提高性能。

不要擅自声称：

- “为了性能优化”
- “为了提高安全性”
- “为了方便维护”
- “作者采用这个结构是因为……”

无法确定原因时，客观描述：

> 当前实现使用……
> 当前代码将……划分为……

**README 应记录项目，而不是替作者编造设计思想。**

---

## 5. 已有 README 的处理

不要无视原 README 从零覆盖。应当：

1. 阅读原 README
2. 理解原作者已提供的信息
3. 与当前代码和结构核对
4. 保留仍准确、有价值的内容
5. 修正过时内容
6. 补充缺失内容
7. 重组结构
8. 删除重复、空泛、错误内容

目标是得到更好的 README，不是简单覆盖。

---

# 二、README 的核心读者

## 1. 普通用户

最关心：

1. 这是什么？解决什么问题？
2. 有什么主要功能？
3. 需要什么环境？
4. 安装什么？如何安装？
5. 如何运行？最简单的用法是什么？
6. 输入什么？输出什么？
7. 运行成功是什么样？
8. 出错怎么办？

用户部分应：简洁、直接、可操作、信息密度高、少讲内部实现。

**普通用户应能在很短时间内完成第一次运行。**

---

## 2. 开发者

最关心：

1. 项目如何组织？用了什么技术？
2. 核心模块是什么？如何协作？
3. 程序从哪里开始？主要执行流程是什么？
4. 数据如何流动？核心逻辑在哪里？
5. 关键设计为什么这样实现？
6. 如何增加 / 修改 / 替换功能？
7. 如何构建、测试、发布、部署？
8. 当前有什么限制？

开发者部分应明显更深入，根据实际提供：

- 项目结构、技术栈、系统架构
- 模块说明、执行流程、数据流
- 核心类 / 函数、关键设计
- 配置机制、异常处理、测试体系
- 构建 / 发布 / 部署、扩展方式、已知限制

---

# 三、用户友好性：提供完整操作路径

README 不应只是信息集合，而应让用户沿着文档一步步完成：

```text
认识项目
  ↓
确认环境要求
  ↓
准备运行环境
  ↓
安装全部必要依赖
  ↓
准备必要资源
  ↓
完成配置
  ↓
第一次运行
  ↓
确认运行成功
  ↓
正式使用
  ↓
遇到问题时排查
```

**核心不是写更多，而是让“下一步做什么”始终明确。**

不要假设用户知道下一步。应主动告诉用户：

- 现在做什么
- 在什么目录执行
- 执行什么命令
- 哪些内容需要替换
- 成功后应看到什么
- 下一步做什么

---

## 1. 明确区分用户操作阶段

### 阶段一：认识项目

这是什么、解决什么问题、主要功能、适合什么场景。

### 阶段二：环境准备

操作系统、语言版本、运行时、编译器、Git、CUDA、数据库、外部软件、模型 / 数据集等。

### 阶段三：安装

需要安装哪些依赖、是否有依赖文件、是否需要虚拟环境、应执行什么完整命令。

### 阶段四：配置

是否需要配置文件、环境变量、API Key、修改路径、准备模型；哪些是必须的。

### 阶段五：第一次运行

从哪个目录运行、用什么命令、是否需要参数、正常应出现什么、输出保存在哪里。

### 阶段六：正式使用

常用参数、常用功能、不同模式、高级配置、批量处理、自定义功能。

### 阶段七：故障排查

如何判断问题、可能原因、解决方法、解决后重新执行什么。

---

## 2. 快速开始必须是最短成功路径

目标是让第一次接触项目的人以尽可能少步骤完成第一次成功运行。

推荐结构：

```text
第 1 步：获取项目
第 2 步：安装环境
第 3 步：准备必要文件
第 4 步：运行
第 5 步：确认结果
```

每一步都应：

- 给出具体命令
- 说明该命令作用
- 说明执行后应看到什么

如果某步在当前项目中不存在，不要为了形式强行增加。

---

## 3. 快速开始必须说明“成功标志”

不要只写：

```bash
python main.py
```

还应说明：

- 终端正常会出现什么
- 会生成什么文件
- 文件保存在哪里
- GUI 会出现什么界面
- 什么现象代表成功

例如：

```text
运行完成后，项目目录下会生成：

output/
└── result.pdf
```

用户才能判断程序是真成功，还是只是没报错。

---

# 四、环境准备必须完整

“环境准备”不能只列几个软件名。应根据实际项目回答：

- 操作系统
- 编程语言及版本
- 编译器、包管理器、运行时
- 外部软件
- GPU / CUDA
- 数据库
- 浏览器或驱动
- 其他系统依赖

必须区分：

> **运行项目需要什么**
> **开发项目需要什么**

例如某个 IDE 只是开发者工具，普通用户运行程序并不需要，就不应写成运行前置条件。

---

## 1. 环境准备检查清单

建议在环境准备末尾提供检查清单：

```text
[ ] 已安装 Python 3.10+
[ ] 已安装 Git
[ ] 已安装 FFmpeg
[ ] 已确认命令行可以运行 python --version
```

---

## 2. 不同操作系统的说明

如果 Windows、macOS、Linux 操作完全一致，不需要重复三遍。

如果存在差异，明确区分：

```markdown
### Windows

...

### macOS / Linux

...
```

尤其注意：路径、shell 命令、虚拟环境激活方式、编译器、系统依赖、权限、可执行文件、GPU / CUDA、外部软件。

不要只写“支持 Windows、macOS 和 Linux”，却不给出实际差异。

---

# 五、依赖安装：尽可能降低用户操作成本

优先使用项目已有的标准依赖文件：

- `requirements.txt`
- `pyproject.toml`
- `poetry.lock`
- `package.json`
- `package-lock.json`
- `CMakeLists.txt`
- `pom.xml`
- `build.gradle`

这些文件比人工猜测依赖更可靠。

---

## 1. 有依赖文件时

Python：

```bash
python -m pip install -r requirements.txt
```

Node.js：

```bash
npm install
```

C++（以实际构建系统为准）：

```bash
cmake -S . -B build
cmake --build build
```

Java（以实际构建文件为准）：

```bash
mvn install
```

或：

```bash
gradle build
```

**不要机械套用某一种语言的模板，命令必须来自项目实际构建方式。**

---

## 2. 没有依赖文件时

如果能够从项目实际代码和配置中确认依赖，应尽量给出完整安装命令：

```bash
python -m pip install package-a package-b package-c
```

而不是：

```text
请安装 package-a。
请安装 package-b。
请安装 package-c。
```

**能合并成一条完整命令，就优先提供一条完整命令。**

但必须遵守：

> **只安装项目实际需要的依赖。**

不能把“可能有用”“曾经用过”“猜测需要”的库全部加入。

---

## 3. 虚拟环境

如果项目适合使用 Python 虚拟环境，应提供完整流程，而不是只写“建议使用虚拟环境”：

```bash
python -m venv .venv
```

激活后：

```bash
python -m pip install -r requirements.txt
```

如果项目不需要虚拟环境，不必强行增加。

---

## 4. 一键安装脚本

如果项目实际存在：

- `setup.bat`
- `setup.ps1`
- `setup.sh`
- `install.py`
- 其他安装脚本

应明确告诉用户：

- 脚本名称
- 使用平台
- 如何执行
- 脚本完成了什么
- 执行完成后的下一步

如果项目不存在安装脚本：

**绝对不能假装项目存在一键安装脚本。**

用户友好不等于编造功能。

---

## 5. 安装验证命令

安装完成后，应提供一条简单验证命令，让用户确认安装成功：

```bash
python -c "import numpy; print(numpy.__version__)"
```

或：

```bash
pip list
```

---

# 六、明确用户需要自行准备的资源

有些项目安装完依赖仍不能直接运行，例如需要：

- 模型文件、权重文件
- 数据集、输入文件
- API Key、`.env`
- 数据库、外部程序
- 特定目录、特定硬件、CUDA、浏览器驱动

必须明确说明：

```text
运行前还需要准备：

1. xxx
2. xxx
3. xxx
```

并尽可能说明：

- 从哪里获得
- 文件名是什么
- 放在哪里
- 是否必须
- 缺少后会发生什么

**不要让用户运行到一半才发现缺少关键资源。**

---

## 环境安装与项目配置必须形成连续流程

不要把相关信息分散到 README 各处，让用户自己拼接。

如果实际流程是：

```text
安装 Python
  ↓
创建虚拟环境
  ↓
安装依赖
  ↓
下载模型
  ↓
修改配置文件
  ↓
运行程序
```

README 就按这个顺序组织。

用户不应读完“安装”后才在十几页后发现：原来还需要下载模型。

---

# 七、使用方法

必须基于项目实际功能编写。

## 1. 命令行程序

```bash
program [选项] <输入>
```

解释真实参数：

| 参数    | 说明 | 默认值 |
| ------- | ---- | ------ |
| `--xxx` | xxx  | xxx    |

## 2. GUI

应说明：

1. 如何启动
2. 主界面有哪些功能
3. 用户需要做什么操作
4. 每个重要按钮或区域的作用
5. 程序产生什么结果
6. 结果保存在哪里

## 3. 库 / API

提供最小可运行示例。

## 4. 使用方法分层

建议分两层：

- **基础用法**：覆盖 80% 场景
- **进阶用法**：参数组合、批处理、配置文件、脚本调用

用户先掌握基础用法，再按需深入。

---

# 八、输入与输出

如果项目有明确输入输出，应单独说明：

- 支持什么输入
- 输入格式、必要字段
- 输出格式、输出位置
- 文件命名规则
- 特殊情况

例如：

```text
输入文件
  ↓
读取
  ↓
处理
  ↓
输出文件
```

对于数据处理、转换、分析类程序尤其重要。

尽可能提供真实、可复制的输入输出示例：

```text
输入：
input/example.txt

内容：
...

执行：
python main.py input/example.txt

输出：
output/example_result.txt

内容：
...
```

---

# 九、真实使用示例

如果项目适合展示示例，应提供**真实、可复制、与当前代码一致**的示例。

优先使用：

```text
输入
  ↓
执行
  ↓
输出
```

或：

```bash
实际命令
```

配合：

```text
实际输出
```

示例中的命令、参数、文件、路径、输出都必须能从项目实际情况得到依据。

**绝对不要编造不存在的命令、参数、文件或输出结果。**

---

# 十、配置说明

如果项目存在配置文件、环境变量、命令行参数、用户设置、配置目录，应集中说明：

| 配置项 | 作用 | 默认值 | 是否必须 |
| ------ | ---- | ------ | -------- |
| `XXX`  | ...  | ...    | 是       |

如果配置文件较复杂，可进一步解释配置结构。

---

# 十一、常见问题与故障排查

只记录真正可能遇到的问题：

```markdown
### xxx 错误

原因：

...

解决：

...
```

如果能够从代码判断错误来源，应尽可能说明具体原因。

不要为了看起来“完整”而制造不存在的问题。

常见问题应优先覆盖环境准备和安装阶段：

- `python` 命令找不到
- `pip` 命令找不到
- 依赖安装失败（网络、版本冲突）
- 虚拟环境未激活
- 权限不足
- 系统缺少某个工具

这些最容易卡住新用户。

---

## 对可能失败的步骤提前提醒

如果某步有明显前置条件，应在命令之前说明，而不是等用户报错：

```text
注意：

执行下面命令前，请确保已经进入项目根目录。
```

或：

```text
注意：

首次运行需要提前准备 model.pt，并放置在 models/ 目录。
```

# 十二、用户部分与开发者部分必须形成明确边界

推荐：

```text
项目介绍
  ↓
快速开始
  ↓
环境与安装
  ↓
基本使用
  ↓
输入输出
  ↓
配置
  ↓
常见问题

开发者文档
  ↓
项目结构
  ↓
架构
  ↓

  ↓

  ↓
测试
  ↓
构建
  ↓
扩展
```

普通用户不需要阅读开发者部分就能运行项目。

# 十三、开发者部分

开发者部分是 README 与普通项目介绍最重要的区别。复杂项目中应明显比用户部分更深入。

---

## 1. 项目结构

根据实际目录生成：

```text
project/
├── src/
│   ├── core/
│   ├── utils/
│   └── ...
├── tests/
├── docs/
├── examples/
├── README.md
├── requirements.txt
└── LICENSE
```

解释重要目录和文件：

| 路径         | 作用     |
| ------------ | -------- |
| `src/core/`  | 核心逻辑 |
| `src/utils/` | 通用工具 |
| `tests/`     | 测试     |
| `main.py`    | 程序入口 |

不要把每个无意义小文件都解释一遍。  
但看起来普通、实际承担重要职责的文件应当说明。

---

## 2. 技术栈

明确列出项目实际使用的技术：

```text
- 编程语言：Python
- GUI：PySide6
- PDF 处理：PyMuPDF
- 构建工具：...
- 测试框架：...
```

正式技术名称可保留英文。  
如果某项只是开发工具而非运行时依赖，应明确区分。

---

## 3. 系统架构

对有一定复杂度的项目，说明整体架构。重点回答：

> **程序由哪些核心部分组成？这些部分之间如何协作？**

优先使用普通 Markdown、列表、表格、纯文本箭头：

```text
输入
  ↓
解析
  ↓
核心逻辑
  ↓
处理
  ↓
输出
```

**禁止使用 Mermaid、PlantUML、Graphviz DOT 等需要特殊渲染器的图表语言。**

如果纯文本已能表达清楚，就用纯文本。  
只有确实需要图形化展示，且项目已有真实图片资源时，才考虑使用图片。

---

## 4. 核心执行流程

说明程序从启动到结束的大致过程：

```text
程序启动
→ 加载配置
→ 验证输入
→ 读取数据
→ 核心处理
→ 生成结果
→ 保存或展示结果
```

复杂项目应进一步说明：初始化、关键分支、模块调用顺序、异常路径、退出流程。

---

## 5. 核心模块

逐个解释真正重要的模块。每个模块至少说明：

- 职责
- 输入、输出
- 与其他模块的关系
- 关键实现方式
- 是否可独立替换
- 修改时需要注意什么

**不要逐行解释代码。README 解释结构和设计，而不是代替源代码。**

---

## 6. 核心数据流

如果项目有明显数据流，应解释：

```text
输入数据
  ↓
解析
  ↓
内部数据结构
  ↓
核心处理
  ↓
结果对象
  ↓
输出文件
```

重点说明：

- 数据从哪里产生
- 使用什么结构保存
- 在哪里转换
- 哪个模块处理
- 最终如何输出

复杂项目中，这部分往往比目录说明更重要。

---

## 7. 关键设计与实现

对值得开发者理解的设计，应解释：

- 当前实现采用什么方案
- 为什么使用某个库
- 为什么采用某种数据结构
- 为什么拆分成当前模块
- 哪些设计涉及兼容性、可维护性、技术权衡、特殊处理

但必须注意：

**不要编造作者没有做过的设计决策。**

无法确定原因时，客观描述：

> 当前实现采用……

而不是：

> 作者为了提高性能，所以……

---

## 8. 接口、类与函数

如果项目存在公开 API、类、函数、命令行接口，应提供开发者级说明：

```markdown
### `parse_document(path)`

读取并解析指定文件。

**参数**

- `path`：输入文件路径。

**返回值**

解析后的文档对象。

**异常**

...
```

对于类，可说明职责、成员、构造方式、重要方法、输入输出、使用关系。

不要把每个简单 getter/setter 都写成长篇说明。

**说明深度应与接口的重要程度匹配。**

---

## 9. 错误处理

如果项目存在较明确的异常处理机制，应说明：

- 错误类型
- 错误产生位置
- 错误传播方式
- 用户看到什么
- 开发者如何定位
- 日志在哪里
- 是否自动恢复

---

## 10. 测试

如果项目存在测试，应说明：

- 使用什么测试框架
- 测试目录在哪里
- 如何运行
- 覆盖哪些核心功能
- 是否存在测试数据
- 是否有特殊测试环境要求

例如：

```bash
pytest
```

如果没有测试：

**不要虚构测试体系。**

可以客观说明：

> 当前项目暂无自动化测试。

如果只有部分手工测试，也应如实说明。

---

## 11. 开发环境

如果项目有明确开发环境，应说明：

- 编程语言版本
- IDE、编译器、构建工具、包管理器
- 必要 SDK、操作系统、开发依赖

必须区分：

> **运行项目所需环境**
> **参与开发所需环境**

---

## 12. 构建、打包、发布与部署

如果项目存在编译、构建、打包、发布或部署流程，应根据实际情况说明：

- 开发环境
- 构建命令
- 构建过程
- 输出产物
- 打包方式
- 发布流程
- 部署方法
- 平台差异

不要因为某个项目没有发布流程，就强行创建“发布”章节。

例如普通 Python 脚本直接运行：

```bash
python main.py
```

就没有必要虚构复杂“部署架构”。

---

## 13. 扩展与二次开发

对于有持续开发价值的项目，应说明：

> **如果开发者想增加一个新功能，应该从哪里开始？**

例如：

```text
新增处理器
→ 创建新模块
→ 实现统一接口
→ 注册到对应模块
→ 添加测试
→ 更新配置
```

如果项目使用插件机制、注册表、工厂模式等，也应根据实际实现说明。

---

# 十四、复杂项目的额外要求

如果项目具有多个核心模块、多种输入输出、GUI + 命令行、数据库、网络服务、插件系统、多线程 / 异步、复杂配置、多平台支持、编译系统、多个外部依赖，则不能只写：

> 项目简介 + 安装方法 + 简单目录。

应根据实际情况增加：

- 系统架构、模块关系、数据流
- 生命周期、配置系统、接口、扩展机制
- 构建系统、测试体系、部署方式
- 性能注意事项、平台兼容性、已知限制、重要设计取舍

如果项目规模非常大，可以按模块拆分开发者文档，但 README 仍应承担“总入口”职责。

---

# 十五、篇幅控制

README 没有固定字数限制。遵循：

> **最小项目，最小文档；复杂项目，完整文档。**

不要为了“详细”强行写长，也不要因为害怕长而删除真正有价值的信息。

尤其注意：

> **宁可增加技术信息，也不要增加空泛描述。**

一个包含 20 个源文件的项目，README 比 100 行脚本长很多是正常的。  
一个复杂架构项目，README 达到数千字甚至更多也合理。

但：

> **README 的目标不是尽可能长，而是信息密度尽可能高。**

如果某段内容不能帮助用户使用、开发者理解、维护或扩展项目，就应考虑删除。

---

# 十六、代码、命令与项目结构

所有代码、命令、路径、参数必须尽量来自实际项目。

代码块应注明语言：

```bash
python main.py
```

```python
from xxx import xxx
```

路径必须与项目实际结构一致。

不要出现：

```text
your_project/
your_file.py
some_command
```

这种仅用于凑格式的占位内容，除非确实需要用户自行替换。

如果确实存在需要用户替换的变量，应明确说明：

```bash
python main.py <你的文件路径>
```

而不是假装这是真实文件名。

---

# 十七、版本与兼容性

如果项目能确定版本信息，应说明：

- 当前版本
- 支持的语言版本
- 支持的操作系统
- 关键依赖版本
- 已测试平台
- 平台差异

如果无法确认，不要自行编造版本号。

如果代码实际没有跨平台测试，也不要写：

> 完全支持 Windows、macOS 和 Linux。

应客观描述当前能确认的信息。

---

# 十八、截图、图片与可视化内容

如果项目是 GUI、可视化工具、图像处理工具、数据分析工具、有明显交互界面的应用，可考虑加入截图、GIF、架构图、流程图、输出示例。

但只有在能真正帮助用户理解项目时才加入。

不要为了“看起来专业”加入没有信息价值的图片。  
如果当前环境无法获得真实截图，也不要伪造截图。

---

# 十九、流程图、架构图与特殊标记语言

README 中如果需要表达程序执行流程、数据流、模块调用关系、系统架构、文件处理流程、用户操作流程：

**优先使用纯 Markdown 文本、列表以及 ASCII 风格的文字和箭头表达。**

例如：

```text
原始 PDF
  ↓
逐页读取
  ↓
图像处理
  ↓
目标检测
  ↓
文字识别
  ↓
层级修复
  ↓
生成书签
  ↓
输出 PDF
```

或：

```text
输入文件 → 文件解析 → 数据处理 → 结果生成 → 输出文件
```

这种形式具有更好的跨平台兼容性、GitHub / GitLab / 本地编辑器兼容性、可读性、可复制性、长期维护性。

**禁止使用 Mermaid、PlantUML、Graphviz DOT 等需要特殊渲染器或额外支持的图表语言。**

不要为了“看起来更专业”强行加入特殊图表语法。  
如果纯文本已能清晰表达关系，就优先使用纯文本。  
只有项目实际复杂到纯文本难以准确表达，且确实需要图形化展示时，才考虑使用真实图片或项目已有图表资源。  
**不要为了图表而引入额外文档语法依赖。**

---

# 二十、语言与表达风格

README 默认使用**中文**编写。

整体风格：

- 专业、清晰、克制
- 信息密度高、技术准确
- 易于扫描
- 不故作高深、不营销化、不论文腔、不流水账

优先使用：中文标题、小标题、表格、列表、代码块、简短段落。

正式技术名称、库名称、命令、API、类名、函数名可保留英文：

> 使用 `PyMuPDF` 处理 PDF 文件。

而不是强行翻译技术名称。

避免连续大段文字。

---

# 二十一、README 的阅读层次

最终 README 应形成明显阅读层次：

```text
第一层：第一次看到项目
        ↓
        知道它是什么、能干什么

第二层：想使用它
        ↓
        能快速准备环境、安装并运行

第三层：想深入使用
        ↓
        知道参数、配置、输入输出

第四层：想开发它
        ↓
        理解目录、模块、架构和数据流

第五层：想维护 / 扩展它
        ↓
        理解设计、测试、构建和扩展方式
```

README 不应要求普通用户阅读完整篇文档才能开始使用。  
同时，开发者也不应因为 README 过度简略，而必须自行阅读大量源代码才能弄清大致结构。

---

# 二十二、信息优先级

如果需要在“完整”和“简洁”之间取舍，优先保留：

### 第一优先级：项目是什么

- 项目用途、核心功能、适用场景

### 第二优先级：怎么使用

- 环境、安装、快速开始、基本用法、输入输出

### 第三优先级：怎么理解

- 项目结构、技术栈、架构、核心模块、执行流程

### 第四优先级：怎么继续开发

- 接口、设计、测试、构建、扩展、部署

如果项目规模很小，不应为了写满这些内容而强行制造内容。

---

# 二十三、信息缺失时的处理

- **可以确认**：直接写
- **可从代码合理推断，但不是绝对确定**：使用客观、保守表达
- **完全无法确认**：不要编造，可省略、标记“待补充”，或说明“当前项目未提供相关信息”

**不要为了让 README 看起来完整而制造事实。**

# 二十四、License

所有 README 一律采用如下声明：

## License

本项目代码仅供学习、研究与个人使用。未经作者许可，禁止将本项目用于商业用途、直接复制后重新发布，或以本项目及其衍生代码作为独立项目进行再发布。

如果项目中已经存在明确的 LICENSE 文件，应结合项目实际情况处理，但不得擅自把其他许可证改写成上述声明。

**不要自行声称项目采用 MIT、Apache、GPL 等许可证，除非项目实际存在对应许可证。**

# 二十五、开发路线与参与开发

## 开发路线

只有当项目确实存在未来计划时才写。不要虚构开发计划。  
如果项目已经稳定，或作者没有明确未来计划，可以不写。  
如果确有路线图，只记录能从项目资料确认的内容。

## 参与开发

如果项目是个人小工具，不需要为套模板强行加入复杂贡献指南。

如果项目具有多人协作或开源属性，可说明：

- Issue、Pull Request
- 开发规范、测试要求
- Commit 规范、分支策略
- 代码风格、提交要求

所有内容以项目实际情况为准。

# 二十七、用户操作链最终检查

在生成 README 前，必须从完全不了解项目的新用户视角，把实际操作链重新走一遍：

```text
我拿到项目后
  ↓
我知道它是什么了吗？
  ↓
我知道需要什么环境了吗？
  ↓
我知道应该先安装什么了吗？
  ↓
我能一次性安装全部必要依赖吗？
  ↓
我知道还需要准备哪些文件 / 配置了吗？
  ↓
我知道命令应该在哪个目录执行了吗？
  ↓
我能直接复制命令吗？
  ↓
我知道运行命令是什么了吗？
  ↓
我知道什么现象代表运行成功了吗？
  ↓
我知道输出在哪里了吗？
  ↓
出错后我知道应该先检查什么了吗？
```

如果其中任何一个关键环节只能依靠用户“自己猜”“自己搜索”或“自己看源码”，应优先补充 README。

---

## 不要把 README 写成“知识考试”

用户执行项目时，不应被迫回答：

```text
Python 应该用 pip 还是 pip3？
应该进入哪个目录？
requirements.txt 应该怎么安装？
这个模型文件放哪里？
这个参数是不是必须？
这个脚本先运行还是后运行？
```

如果这些问题可以由 README 根据项目实际情况明确回答，就应直接回答。

**README 的职责之一，就是替用户消除这些不必要的决策成本。**

但对于确实存在多个合理方案的地方，应明确说明差异，而不是假装只有一种方案。

---

# 二十八、最终要求

请把这次任务理解为：

> **为这个项目制作一份真正可以放进 GitHub / GitLab 项目根目录、供用户和开发者长期使用的正式 README。**

不要把任务理解为：

> “按照固定模板生成一篇 README。”

更不要因为本规范列出了很多章节，就认为这些章节全部必须出现。

**规范提供的是判断标准，而不是固定答案。**

最终文档应做到：

**用户看前面很短的一部分，就能理解项目是什么、有什么用，并开始准备和使用；**

**用户继续阅读，可以获得完整的环境准备、依赖安装、配置、运行、输入输出和故障排查信息；**

**开发者继续往下阅读，可以逐步理解项目结构、技术栈、架构、模块、数据流、实现方式和维护方法；**

**项目越复杂，开发者部分越详细；项目越简单，则保持克制；**

**信息宁可完整，也不能敷衍；但是绝不通过重复、套话和无意义章节制造所谓的“详细”。**

最重要的是：

> **先理解项目，再决定怎么写 README。**
>
> **不要先决定 README 应该长什么样，再强行把项目塞进模板。**

如果当前项目已经存在 README，应在充分理解原 README 后进行**重构、补充和改进**，而不是无视已有内容直接覆盖。

如果项目中存在明显缺失但无法从代码确认的信息，应明确指出缺失项，而不是自行编造。

**最终只输出完整的 `README.md` 内容。**

不要输出分析过程。

不要解释你准备如何写。

不要先给出大纲后等待确认。

不要告诉用户“下面我将……”。

**直接完成 README。**
