# 🌐 个人网站导航 · 项目维护规范

> [!summary] 核心目标
> 维护一份适合 Obsidian 长期使用的 **个人网站导航**：**上方 Callout 快速总览，下方按项目完整介绍**。既能立即打开网站、复制完整 URL，也能在需要时阅读项目简介。
>
> **未来每次新增或更新网站时，AI 必须主动访问网页、检索相关公开资料并核实功能，不能要求用户重复解释网站用途，也不能仅凭名称编造简介。**

## 1. 适用范围与目标文件

- **目标文件：** `00_个人网站导航_总览与详情.md`（可改名；以用户提供的最新版为准）。
- **本文件用途：** 约束 AI / 人工对目标文件进行新增、修改、合并和核查；它是**维护规则**，不是网站导航本身。
- **一项目一条记录：** 同一项目即使通过 GitHub Pages、Netlify 等多个平台部署，也只建立 **一个总览 Callout + 一个详细介绍章节**。
- **不同项目分别记录：** 不因名称相似或部署平台相同而合并；先根据内容及源码关系判断。
- **默认交付：** 用户要求“添加网站”“更新导航”时，输出**修改后的完整导航 `.md` 文件**，而不仅是可粘贴片段；若用户明确要求仅给片段则遵从。

## 2. 页面结构（必须保持）

严格按照以下顺序组织：

1. YAML Frontmatter：标题别名、标签、创建与更新日期等。
2. 一级标题：`# 🌐 个人网站导航`。
3. 简短导航说明 Callout：一句话说明导航用途即可。
4. `## 🚀 网站总览`：**每个项目一个简短 Callout**，负责快速访问和页内跳转。
5. 分隔线 `---`。
6. `## 📖 项目介绍`：**每个项目一个三级标题及正文介绍**。
7. 必要时在末尾使用 `> [!warning] 待确认信息`，统一记录无法核实的事项；无事项时可省略。

> [!important] 版式约束
> - **不要把总览改成宽表格**，避免 Obsidian 桌面端和移动端横向滚动。
> - 不将所有功能简介塞进顶部 Callout；上方只负责导航，**下方必须保留正常展开的项目简介与主要功能**。
> - 不使用折叠语法替代下方正文，不要求安装 Dataview、HTML 插件或主题插件。
> - 适量采用不同类型的 Obsidian 原生 Callout，起到语义分组作用，不为装饰而堆砌。

## 3. 网站总览：固定四项信息

每个项目都必须包含以下四项，且顺序不变：

| 字段 | 规范 |
|---|---|
| 网站名称 | 项目正式名称，可加一个匹配用途的 Emoji；作为 Callout 标题 |
| GitHub Pages | 项目的 GitHub Pages **网页入口**；没有或确认尚未部署时写「暂无」 |
| 其他入口 | Netlify、Vercel、自定义域名等其他访问地址，标明平台；没有写「暂无」 |
| GitHub 源码 | GitHub **源代码仓库页面**，不能与 GitHub Pages 站点混淆；没有写「暂无」 |

另加一行：`[[#与下方完全一致的项目标题|📖 查看项目介绍]]`，用于页内跳转。

### 3.1 链接必须同时可点击、可复制

**统一使用 Markdown 自动链接：** `<https://example.com/>`。

- 渲染后直接显示**完整的网址**，同时整个网址**可以点击跳转**。
- 尽量保留官网实际使用的路径、大小写和尾部 `/`，不要自行更改。
- 不只显示 `[点击访问](...)` 这类隐藏完整地址的文字链接。
- 不将 URL 单独包裹在反引号中作为代码，因为那样通常无法直接点击。
- 不把源码仓库地址误写成 Pages 网址，或根据仓库名**猜测** Pages 地址。
- 多个备用入口分别列出；没有对应平台时写「暂无」，不生成空链接。

### 3.2 顶部 Callout 模板

> [!note] 使用说明
> 下方 `项目名称`、`项目介绍标题` 和 `example.com` 都是**待替换占位内容**，不能原样当作真实项目发布。

```markdown
> [!info] 🌐 项目名称
> **GitHub Pages（主入口）：** <https://example.com/>  
> **其他入口（Netlify）：** <https://example.netlify.app/>  
> **GitHub 源码：** <https://github.com/owner/repository>  
> [[#项目名称 · 项目介绍标题|📖 查看项目介绍]]
```

如果 GitHub Pages 尚不存在，则写：

```markdown
> **GitHub Pages：** 暂无  
```

如果备用入口有多个，逐行写 `**其他入口（平台名）：** <https://...>`，不要用一个很长的横向字段串接所有地址。

> [!tip] 主入口优先级
> **主入口由用户指定，不能擅自更改。** 例如「知栈 · HTML 知识库」以 **GitHub Pages 为主入口、Netlify 为其他入口**。其他新项目如果未指定主次，可如实列出地址而不额外标注“主入口”；若需排序优先，将用户指定的主要访问方式放在前面。

## 4. 项目介绍：正常展开、信息准确

每个总览 Callout 必须在下方有一个**同名且唯一**的三级标题。详情包含：

1. **项目定位：** 1～3 句话，说明这个网站解决什么问题、面向什么使用场景；不写空泛宣传语。
2. **主要功能：** 按公开证据整理 3～6 条关键功能（功能较少时据实减少）；描述实际具备的功能，而非主观设想。
3. **部署方式：** 简要解释 GitHub Pages / 其他平台的关系；有必要时补充源码仓库的用途。
4. **页内返回：** `[[#网站总览|↑ 返回网站总览]]`。

下方详情不必反复粘贴总览里的三个网址，除非有额外的文档地址、使用说明或确有解释价值的链接。

### 4.1 下方介绍模板

```markdown
### 项目名称 · 项目介绍标题

**项目定位：** 基于实际网页与公开项目资料写出准确、具体的介绍。

**主要功能：**

- **功能一：** 说明确实已经实现的能力。
- **功能二：** 说明功能适用的场景或交互方式。
- **功能三：** 根据核实情况补充，不强行凑数。

**部署方式：** 说明主入口、其他部署入口及源码关系。

[[#网站总览|↑ 返回网站总览]]
```

> [!warning] 禁止编造
> 不得把“项目计划实现”“README 愿景”“演示界面中的占位按钮”写成**已经上线的实际功能**；功能必须有可核实依据。拿不到可靠内容时，写「待核实」，并说明具体缺什么，不要凭网站名称想象功能。

## 5. AI 新增网站时的强制调研流程

> [!important] 这是必须执行的要求，不是可选建议
> **用户只需提供一个或多个网站链接。AI 负责自己打开、检索、阅读、比较和提炼项目介绍；原则上不要求用户先介绍网站用途。**

### 步骤 A｜逐个访问网站

1. 打开用户提供的**每一个**网页链接，观察首页名称、导航菜单、功能区、页面文字和使用流程。
2. 如果网站有「关于」「帮助」「功能介绍」「文档」「更新日志」等页面，按需要继续查看。
3. 判断是已上线产品、作品演示、文档站点，还是尚未完成的占位页；仅记录实际有依据的信息。
4. 区分网站访问地址和代码仓库地址，不将二者混为一谈。

### 步骤 B｜主动检索公开资料

1. 搜索**网站名称、域名、项目名称及可能关联的 GitHub 仓库**。
2. 优先核查项目自己的**官方网页、GitHub README、仓库说明、文档和 Release / Changelog**；必要时阅读公开源码以验证关键功能。
3. 用其他可信公开资料辅助核对；不同来源矛盾时优先最新、最直接、能复核的证据，避免简单拼接。
4. 通过仓库归属、页面链接、项目描述或部署配置来确认同一项目的多平台地址，**不能因为名字相像就认定属于同一项目**。
5. 检查 GitHub Pages 是否有**明确、实际的部署证据**。不能仅凭 `用户名.github.io/仓库名/` 的命名规则推定已经发布。

### 步骤 C｜核对真实性与状态

- **可确认：** 写入已证实的名称、平台、网址和实际功能。
- **网页不能访问，但官方 README / 文档可确认：** 可以依据官方资料写简介，但不要宣称“已直接浏览网站并确认页面正常运行”。
- **只有线索，无法验证：** 相应功能或地址标记为「待核实」，不把推断写成事实。
- **确实没有入口或源码：** 写「暂无」。
- **不能确定是没有还是没查到：** 写「待核实」，而不是武断写「暂无」。
- **无法从当前工具环境打开网页：** 继续尝试项目官方资料或公开仓库；仍无法核实时如实说明局限。不得虚构访问结果、HTTP 状态或网站可用性。

### 步骤 D｜归纳和更新

1. 判断该链接是否属于导航中**已有项目的另一部署入口**；若是，更新原有 Callout 和详情，不新增重复项目。
2. 若属于新项目，在总览增加一个 Callout，同时在项目介绍区增加对应标题和正文。
3. 自行提炼简洁但有信息量的介绍，保持项目之间详细程度基本一致，不复制整篇 README。
4. 更新 Frontmatter 中的 `updated` 日期（以实际编辑日期为准）；`created` 保留原日期。
5. 保留已有项目的信息、链接、主备入口顺序、标题和相邻说明；未经要求，不擅自改写其他项目。

## 6. 内部链接与 Obsidian 兼容性

- **查看项目介绍：** `[[#下方标题的完整文字|📖 查看项目介绍]]`。
- **返回总览：** `[[#网站总览|↑ 返回网站总览]]`。
- 下方标题应与总览跳转目标**逐字一致**，避免中文标点、空格或项目改名导致跳转失败。
- 全文只使用标准 Markdown + Obsidian 原生 Callout / WikiLink；不依赖第三方插件。
- 新增项目后，检查所有内部跳转、外部 URL 是否符合格式。
- 页面优先垂直排版、短段落、短列表；不制造需要横向滚动的导航表格。

## 7. 更新纪律与核查清单

> [!check] 每次交付前逐项核对
> - [ ] 每个项目都有且只有一个顶部 Callout，以及一个下方介绍章节。
> - [ ] 总览完整显示：网站名称、GitHub Pages、其他入口、GitHub 源码。
> - [ ] 所有真实网址都以可点击且显示完整 URL 的形式出现；缺失信息写「暂无」或「待核实」。
> - [ ] 主入口按用户明确要求排序；同一项目的不同部署没有拆成多个项目。
> - [ ] AI 已自行尝试访问每个新增网页，并检索官网、官方文档或 GitHub 资料。
> - [ ] 简介、功能、部署关系有依据；没有把计划功能或推测当成既成事实。
> - [ ] 「查看项目介绍」和「返回网站总览」能够正确对应标题。
> - [ ] 顶部保持简短，下方简介正常展开，没有宽表格、插件依赖和无关元叙述。
> - [ ] 保留原有项目内容并更新修改日期；输出完整 `.md` 文件。

## 8. 可直接交给 AI 的任务指令

> [!example] 追加新网站时，复制下面这段话即可
> 请以《个人网站导航 · 项目维护规范》为最高维护要求，在我提供的最新版《个人网站导航》Markdown 中新增或更新以下网站：
>
> 【粘贴一个或多个网站链接】
>
> 你必须自行逐个浏览网页、检索官网和 GitHub 项目文档，核实网站用途、核心功能、各部署平台与源码仓库；将同一项目的多平台部署合并记录。保留顶部紧凑 Callout 快速总览、完整可点击可复制的网址、页内跳转，以及下方正常展开的准确项目介绍。没有证据的内容明确写「暂无」或「待核实」，不得猜测。不要擅自改动已有项目。最后给我修改后的完整 `.md` 文件。

---

**维护原则一句话：** **先调查核实，再合并归类；上方快速访问，下方完整介绍；链接既能点击也能复制；未知内容绝不编造。**
