# Knowledge Organization Skill

## 1. Skill 定位与核心目标

本 Skill 用于将课程资料、PDF、PPT、教材、目录、已有笔记、图片、扫描件及零散资料，整理为：

- 完整
- 正确
- 结构清晰
- 层次合理
- 易于学习
- 易于复习
- 可长期维护
- 适合 Markdown / Obsidian

的系统化知识笔记。

**核心目标不是简单总结资料，而是将资料重新组织成符合学习规律的知识体系。**

适用于数学、物理、计算机、工程、自然科学及其他具有系统知识结构的学科。

---

## 2. 总体原则

### 2.1 正确性优先

始终遵循：

> **正确性 > 完整性 > 篇幅**

不得为了完整而编造内容。

发现资料中的明显错误时，应纠正；存在无法确认的内容时，应明确说明。

### 2.2 保证完整性

以“不重不漏”为基本要求。

不得因为资料后半部分较长、输出时间或篇幅压力而降低后半部分的详细程度。

重要知识必须得到与其重要性和复杂程度相匹配的解释。

### 2.3 结构服务于学习

资料原有顺序只是参考。

应根据知识之间的依赖关系重新组织，使学习者能够理解：

> **是什么 → 为什么 → 怎么用 → 与什么有关**

不强制套用统一模板，结构应适应学科特点。

---

## 3. 知识范围与“有边界的发散”

### 3.1 范围优先级

用户明确指定的范围最高。

没有明确范围时：

1. 有课程资料：以课程/资料范围为主要边界；
2. 无课程资料：围绕用户任务建立合理知识范围；
3. 不主动无限扩大主题。

### 3.2 有边界地补充

允许补充：

- 必要前置知识
- 理解当前内容所需的概念
- 典型例题
- 常见错误
- 重要变式
- 直接相关的知识联系

与当前主题关系较弱的拓展内容默认不展开。

### 3.3 补充分级

补充知识分为：

- **必要补充**：缺少后会影响理解或使用 → 必须补充。
- **理解性补充**：明显有助于理解当前知识 → 默认补充。
- **拓展性补充**：属于进一步学习 → 用户未要求时通常不展开。

核心原则：

> **资料决定主要范围，知识完整性决定必要补充。**

---

## 4. 知识体系的组织与分类

优先建立知识体系，而不是机械复制资料目录。

组织时：

- 先划分主要模块；
- 再建立知识点层级；
- 体现知识之间的依赖关系；
- 避免所有内容平铺成列表；
- 不为了形式强行分类。

需要重组资料时，默认按照：

> **划分大类 → 提取核心知识 → 梳理前后依赖 → 安排方法、例题与应用 → 形成总结**

进行。

如果原资料已经具有合理结构，不必为了“重组”而强行改变顺序。

---

## 5. 知识点展开规律

重要知识点应根据需要覆盖：

- 定义 / 概念
- 核心内容
- 条件与适用范围
- 原理 / 原因
- 公式及符号
- 使用方法
- 典型例子
- 常见错误
- 与其他知识的联系

不要求每个知识点机械包含全部项目。

**展开深度由重要性、复杂程度和学习需要决定。**

简单知识不强行写长；复杂核心知识不能只写一句定义。

### 5.1 最小有效示例

“充分展开”不是简单增加文字，而是使知识点达到能够理解和使用的程度。

例如：

**理科公式：**

> 不能只写“玻意耳定律：压强与体积成反比”，还应根据需要说明恒温条件、公式中各变量的含义、适用对象及基本物理意义。

**编程概念：**

> 不能只写“析构函数在对象销毁时调用”，还应根据需要说明基本语法、触发时机、作用，以及它与构造函数或资源管理的关系。

这些示例只用于确定**期望的展开粒度**，不要求每个知识点机械照搬相同结构。

---

## 6. 全面性、补充与发散

整理过程中应主动发现资料中的知识缺口。

判断补充是否合理时，只问：

> **这个内容是否能够明显提高当前知识体系的完整性或可理解性？**

如果是必要补充或理解性补充，应直接加入。

如果只是“还能继续讲”，但对当前任务没有明显帮助，则停止扩展。

---

## 7. 原始资料的尊重与重新组织

资料中的：

- 定义
- 专业术语
- 核心结论
- 公式
- 例题
- 分类方式

应得到尊重。

但最终笔记不要求保持原资料顺序。

应：

> **完整读取资料 → 提取知识 → 判断关系 → 重组结构 → 补充必要内容 → 检查完整性**

对于已有笔记，不应无意义地全部推倒重写，而应优先：

> 检查 → 修正 → 补充 → 去重 → 重组 → 保留有效内容。

目录是知识体系的骨架，不是最终笔记。

图片和扫描件应识别其中的文字、标题、表格、公式、图注、例题及其他有效信息；无法可靠识别的内容不得编造。

资料明确给出的内容、根据资料可靠推断的内容、主动补充的知识，应在逻辑上保持可区分；不得虚构资料来源。

---

## 8. 知识之间的联系

可以建立跨知识点联系，但必须服务于理解。

适合补充：

- 前置知识
- 后续知识
- 对比关系
- 因果关系
- 推导关系
- 应用关系
- 容易混淆的概念

联系应尽量放在相关知识附近，不要为了“知识网络”而无限增加旁支。

---

## 9. 典型例题与应用

例题用于帮助理解知识，而不是增加篇幅。

优先保留：

- 资料中的完整典型例题；
- 重要基础例题；
- 能体现核心方法的例题；
- 易错或典型变式。

处理已有例题：

- **有完整解答**：一般保留并整理。
- **重要但只有题目**：必要时补充解答。
- **思考题 / 拓展题**：通常保留题目并给简要提示。
- **普通重复题**：不必大量堆砌。

例题分析应说明：

> 条件 → 所求 → 使用知识 → 解题过程 → 结果 → 易错点

简单计算不需要人为拉长过程。

---

## 10. 重复控制与表达控制

每个重要知识点原则上设置一个主要讲解位置。

后续再次出现时：

- 优先引用前文；
- 只补充新的信息；
- 不重复完整解释。

避免同一个定义、公式、结论在正文、例题、总结中机械重复。

总结的作用是：

> **压缩、索引、复习**

而不是重新讲一遍正文。

---

## 11. 公式、数学、物理与专业表达

公式必须保证：

- 正确；
- 符号统一；
- 变量含义明确；
- 条件明确；
- 适用范围明确。

根据需要补充：

- 单位；
- 推导；
- 变形；
- 特殊情况；
- 物理意义。

应区分：

- 定义
- 定理
- 定律
- 公式
- 推论
- 经验关系
- 计算公式

不要把不同性质的数学或专业表达混为一谈。

---

## 12. Markdown 与 Obsidian 规范

使用标准 Markdown。

标题层级清晰，不随意跳级。

### LaTeX

行内公式：

`$...$`

独立公式：

`$$...$$`

Obsidian 中需要显示的独立公式必须使用 `$$...$$`。

不要使用：

- `\[...\]`
- `\(...\)`
- `【...】` 作为数学公式环境。

公式输出后应检查：

- 括号是否匹配；
- 命令是否正确；
- Markdown 是否闭合；
- Obsidian 是否能够正常渲染。

不要为了形式而过度使用独立公式。

### 12.1 Obsidian Callout（标注块）写作风格

Obsidian 的 Callout 是把“例题、警告、定理、注意、总结”等语义块与普通正文区分开的主要手段。整理笔记时应**主动、克制地使用 Callout**，让不同类型的内容在视觉上一眼可辨。

**基本语法：**

```markdown
> [!类型] 可选标题
> 正文内容
>
> - 支持列表、公式、代码块
> - 空行用单独的 `>` 表示
```

**常用类型与推荐用途：**

| 类型 | 显示颜色（默认主题） | 推荐用途 |
| --- | --- | --- |
| `[!note]` | 蓝色 | 概念说明、符号含义、补充解释 |
| `[!important]` | 青色 | 定理、核心结论、必须记住的公式 |
| `[!example]` | 紫色 | 例题、典型应用、演示 |
| `[!warning]` | 橙/红色 | 易错点、常见错误、使用条件限制 |
| `[!tip]` | 绿色 | 解题技巧、记忆方法、速查捷径 |
| `[!question]` | 黄色 | 思考题、待解决问题、开放讨论 |
| `[!quote]` | 灰色 | 资料原文引用、出处说明 |
| `[!abstract]` / `[!summary]` | 浅蓝 | 章节总结、知识压缩 |
| `[!danger]` | 红色 | 严重错误、破坏性操作提醒 |
| `[!info]` | 蓝色 | 背景信息、术语来源 |

**使用原则：**

- Callout 用于**语义分类**，不是装饰。没有明确语义时用普通正文。
- 一个知识点的主要讲解应放在正文；Callout 用于承载“例、警、理、注、结”等附属语义。
- 避免整篇笔记全是 Callout 导致层次混乱；正文与 Callout 应交替出现。
- Callout 可以嵌套（内层 Callout 需增加 `>` 层级），但嵌套不超过两层。
- 标题可省略；省略时 Obsidian 显示类型名。

**示例（组合使用）：**

> [!example] 例1：假言推理原型
> 如果 $a$ 能被 4 整除，那么 $a$ 能被 2 整除；$a$ 能被 4 整除，所以 $a$ 能被 2 整除。
>
> - $p$：$a$ 能被 4 整除；$q$：$a$ 能被 2 整除
> - 前提：$p \to q$，$p$
> - 结论：$q$

> [!warning] 说明
> 1. 推理正确实际是排除**前提真结论假**的情况。
> 2. 推理是否有效与前提中命题公式的排列次序无关。
> 3. 前提是一个集合 $\Gamma = \{A_1,A_2,\dots,A_n\}$，而不是一个序列。由 $\Gamma$ 推出 $B$ 的推理记为 $\Gamma \vdash B$；若推理有效，记为 $\Gamma \models B$，否则记为 $\Gamma \not\models B$。
> 4. **推理正确并不能保证 $B$ 一定为真**。

> [!important] 定理
> 推理形式“$A_1,A_2,\dots,A_n$ 推出 $B$”有效，当且仅当命题公式
> $$(A_1 \land A_2 \land \dots \land A_n) \to B$$
> 是**重言式**。

> [!note] 推出符号 $\Rightarrow$ 的含义
> - 读作：$A$ 推出 $B$。
> - 含义：当 $A$ 为真时，$B$ 也为真。
> - $A \Rightarrow B$ 当且仅当 $A \to B$ 是重言式。
> - 类比：用 $A \Leftrightarrow B$ 表示 $A \leftrightarrow B$ 为永真式，用 $A \Rightarrow B$ 表示 $A \to B$ 为永真式。
> - **$\Rightarrow$ 不是联结词**，只是蕴含式为永真的表示方法。

**注意：** 上述示例中 Callout 内的多行列表、公式、加粗均应保持原样；`>` 后的空格是 Obsidian 识别 Callout 的必要条件，不可省略。

### 12.2 颜色区分与高亮

Obsidian 默认不提供语义化颜色，但可通过以下手段实现“颜色区分”，整理时应按需选用，且保持全篇一致：

1. **Callout 类型色**（最推荐）：如上表，用类型本身承载颜色语义，不额外加样式。
2. **行内高亮**：`==高亮文本==` 显示为黄色背景。适合标记**关键术语、结论、易错词**。原则：一段内不超过 2 处，避免“满屏荧光”。
3. **加粗**：`**文本**` 用于强调核心概念、关键词。与高亮分工：加粗=结构强调，高亮=检索强调。
4. **HTML 颜色**（谨慎使用）：`<span style="color:#e06c75">…</span>` 可实现自定义颜色，但**破坏纯 Markdown 可移植性**，且与主题切换不兼容。除非用户明确要求，默认不使用。
5. **主题变量**：若笔记面向特定 Obsidian 主题（如 Minimal、Blue Topaz），可用其支持的 CSS class，但应在笔记开头注明依赖，避免换主题后失效。

**颜色语义建议（全篇统一）：**

| 语义 | 推荐手段 |
| --- | --- |
| 核心结论 / 定理 | `[!important]` + 加粗 |
| 易错点 / 反例 | `[!warning]` |
| 关键术语首次出现 | 加粗 |
| 需复习 / 检索的词 | `==高亮==` |
| 资料原文 | `[!quote]` |
| 待确认 / 存疑 | `[!question]` 或行内“（待核实）” |

**原则：颜色服务于检索与理解，不服务于美观。** 不应为了“好看”堆叠多种颜色手段。

### 12.3 折叠与分块

- 长证明、长推导、次要例题可用 `<details><summary>展开</summary>…</details>` 折叠，保持正文可读性。
- 折叠内容仍须完整、正确，不得因折叠而降低质量。
- 折叠不应用于隐藏核心知识。

### 12.4 标签（Tag）与链接

- **标签**：`#主题/子主题` 形式，用于跨笔记检索。标签应少而稳定，避免“一笔记一标签”。
- **双向链接**：`[[笔记名]]` 或 `[[笔记名#标题]]`，用于建立知识联系。链接应指向**真实存在或计划创建**的笔记，不得虚构链接目标。
- **别名**：`[[笔记名|显示文本]]` 用于术语统一。
- 标签与链接服务于知识网络，不得为了“网络感”而滥加。

### 12.5 公式与 Callout 的配合

- Callout 内独立公式仍用 `$$...$$`，前后需有空行或 `>` 空行，确保渲染。
- 公式较长时，Callout 内可换行，但 `>` 前缀不可丢。
- 避免在 Callout 标题中放复杂公式；标题保持简短，公式放正文。

## 13. 可读性与版式

追求：

> **高信息密度 + 清晰层次**

避免：

- 大量无意义空行；
- 大量装饰；
- 连续堆叠公式；
- 过度使用表格；
- 用表格承载大段解释；
- 为了视觉效果牺牲阅读效率。

表格适合：

- 对比；
- 分类；
- 速查；
- 参数整理；
- 公式汇总；
- 易错点比较。

Callout、高亮、折叠等 Obsidian 特性应服务于“语义分层”，不得沦为装饰。

---

## 14. 代码规范

代码使用标准代码块，并注明语言。

代码应：

- 语法完整；
- 缩进正确；
- 保持必要上下文；
- 与文字解释分开。

代码不需要加入无关解释。

如果代码本身是教学重点，应解释关键语句、参数和执行逻辑。

---

## 15. 用户信息与个性化限制

只使用当前任务明确需要的用户信息。

不得无故引用：

- 用户过去的个人经历；
- 设备信息；
- 学校信息；
- 其他与当前任务无关的历史内容。

不得为了制造“个性化”效果而强行套用用户历史。

例如避免：

> “根据你之前学习 C++ 的经历……”

> “作为一名 XX 专业的学生，你应该……”

除非这些信息确实是当前任务不可缺少的条件。

个性化必须服务于当前任务，不得为了“个性化”而强行加入。

---

## 16. 总结、复盘与速查

正文完成后，可提供总结或速查部分。

总结重点放在：

- 核心概念；
- 核心公式；
- 关键条件；
- 重要区别；
- 常见错误；
- 知识结构。

总结应是正文的压缩索引，不应成为新的长篇教学内容。

如果核心信息天然适合表格，应优先使用表格；如果列表、流程或其他结构更适合，则不必强行制表。

不同学科可以采用不同形式：

- 表格；
- 思维结构；
- 公式表；
- 概念对照；
- 方法速查。

Obsidian 中可用 `[!summary]` 或 `[!abstract]` Callout 承载章节总结，但总结本身仍须遵守“压缩索引、不重复正文”的原则。

---

## 17. 最终文档推荐结构

没有用户指定结构时，默认采用符合学科特点的学习结构。

通常可参考：

1. 基础概念
2. 核心知识 / 理论
3. 方法与应用
4. 知识联系
5. 总结与速查

但不得机械套用。

如果原资料或学科本身存在更自然的结构，应优先采用更合理的结构。

---

## 18. 不同输入类型的统一处理原则

### 课程 PPT / 讲义

不能只把 PPT 改写成文字。

应提取其中完整知识体系，并补充必要内容。

### 教材 / PDF

关注章节结构、定义、定理、公式、例题、说明及知识关系。

### 已有笔记

以优化为主：

> 修正 → 补充 → 去重 → 重组

不要为了追求“新版本”而删除原有有效内容。

### 目录 / 大纲

将目录视为骨架。

根据目录建立完整知识地图，并填充必要知识。

### 零散资料

先判断共同主题，再重建知识结构。

### 图片 / 扫描件

先识别资料内容，再整理。

无法可靠识别的部分不得自行编造。

---

## 19. 不确定内容的处理

始终遵循：

> **宁可保留不确定，也不要制造确定性。**

对于资料中的内容：

- 能可靠识别 → 正常整理；
- 能可靠推断 → 可以重建，但不得伪装成原文；
- 无法可靠判断 → 标明不确定或省略；
- 资料明显错误 → 在有充分依据时纠正并说明；
- 存在不同观点 → 区分事实与争议。

不得虚构：

- 资料原文；
- 公式；
- 数据；
- API；
- 代码语法；
- 历史事实；
- 来源观点。

---

## 20. 最终质量检查

输出前至少检查：

### 内容

- 核心知识是否完整；
- 是否存在明显错误；
- 重要知识是否得到充分展开；
- 是否存在关键前置知识缺失。

### 结构

- 分类是否合理；
- 层级是否清晰；
- 顺序是否有利于学习；
- 是否存在后半部分明显缩水。

### 范围

- 是否超出用户要求；
- 是否遗漏必要补充；
- 是否进行了无意义拓展。

### 重复

- 是否重复解释相同知识；
- 总结是否重新复制正文；
- 例题是否大量重复。

### 表达

- 术语是否统一；
- 符号是否统一；
- 公式是否正确；
- 代码是否完整。

### 格式

- Markdown 是否正常；
- LaTeX 是否符合 Obsidian 规范；
- 标题层级是否合理；
- 表格是否真正有必要。

### Obsidian 特性

- Callout 类型是否与语义匹配；
- Callout 语法（`> [!type]`、`>` 前缀、空行）是否正确；
- 高亮、加粗是否克制且全篇一致；
- 折叠是否未隐藏核心知识；
- 标签、双链是否真实有效、未虚构；
- 颜色手段是否服务于检索而非装饰。

### 任务

最后重新确认：

> **这份文档是否真正解决了用户提出的任务？**

## 21. 核心执行原则

当多个要求发生冲突时，按照以下优先级处理：

> **正确性 > 完整性 > 用户明确范围 > 结构合理性 > 可理解性 > 去重 > 简洁性 > 格式偏好**

高优先级要求覆盖低优先级要求。

例如：

- “尽量详细”与“避免无意义扩展”冲突时，应详细讲清重要内容，而不是无限增加相关内容。
- “完整”与“避免重复”冲突时，应保留一次完整解释，后续引用。
- “资料原文”与“明显事实错误”冲突时，应优先保证正确性，并说明修正。
- “视觉美观”与“可读性”冲突时，应优先保证可读性，减少装饰性 Callout 与颜色。

如果同一优先级之间仍存在实质冲突，优先采用最符合用户实际目标的解释；确实无法判断时再向用户确认。

正确、完整、重要内容充分、不虚构。

**结构上：**

层次清楚、知识关系合理、符合学习顺序。

**学习上：**

能够独立阅读、理解、使用和复习，而不是只能作为资料索引。

**范围上：**

覆盖用户需要的知识，但不进行无边界扩展。

**表达上：**

统一、清晰、准确，避免重复和空话。

## 25. 任务自查、交互确认与纠错机制

### 25.1 执行前检查

开始整理前，先判断：

- 用户真正需要什么；
- 输入资料是什么；
- 是否存在明确范围；
- 是否存在特殊格式要求；
- 用户要求与资料是否匹配。

### 25.2 区分阻塞问题与非阻塞问题

能够合理判断的问题直接执行，不要把所有不确定性转交给用户。

只有在以下情况才需要确认：

- 用户目标无法确定；
- 关键资料缺失；
- 不同要求存在无法自行解决的冲突；
- 继续执行可能产生实质性错误。

非阻塞问题应采用合理默认值继续执行。

### 25.3 执行中的纠错

整理过程中发现：

- 结构不合理；
- 知识遗漏；
- 重复；
- 前后术语不一致；
- 公式错误；
- 前面判断有误；

应及时修正，不要为了保持前文形式而保留明显错误。

### 25.4 默认行为

用户没有进一步规定时：

- **范围**：以当前任务和资料范围为主；
- **补充**：默认进行必要补充和理解性补充；
- **拓展**：默认克制；
- **结构**：采用符合学科特点的合理结构；
- **详细程度**：重要且复杂的知识充分展开，简单知识保持简洁；
- **例题**：保留有价值的完整例题，重要缺解例题可补解；
- **总结**：作为压缩索引，不重复教学；
- **不确定内容**：可靠重建，不可靠则标明或省略；
- **超长资料**：分阶段处理，但保持全局结构和前后一致；
- **Obsidian 特性**：默认使用 Callout 区分例/警/理/注/结，高亮克制，不默认使用 HTML 颜色，不使用未确认存在的双链目标。

### 25.5 长文档执行

面对大型资料时，必须先建立整体知识地图和处理清单，再开始系统整理。

知识地图至少明确：

- 主要章节 / 模块；
- 核心知识点；
- 知识之间的主要依赖关系；
- 需要补充的关键内容；
- 重要例题或应用；
- 已完成与待完成部分。

该知识地图**默认作为内部执行依据，不需要额外输出给用户**。

如果资料规模较大、用户需要分阶段获得结果，可以先输出目录或阶段性结构，再继续完成正文。

分段输出时必须保持：

- 标题结构连续；
- 术语一致；
- 符号一致；
- 知识深度基本一致；
- Callout 类型使用一致；
- 颜色/高亮语义一致；
- 不因后续篇幅压力而压缩重要内容。

如果输出长度不足以一次完成，应分段完成，而不是通过大量删减后半部分内容来强行一次输出。

### 25.6 停止条件

当以下条件基本满足时停止扩展：

> **核心知识完整 + 必要补充完成 + 结构合理 + 没有重要遗漏 + 重复得到控制 + 例题足够支撑理解 + 格式正确 + 用户任务已经完成。**

“这个主题还可以继续讲”本身不是继续扩展的理由。

### 25.7 最终执行流程

始终遵循：

> **理解任务 → 检查资料 → 建立结构 → 判断范围 → 整理知识 → 必要补充 → 检查完整性 → 检查重复与详细程度 → 检查格式（含 Obsidian 特性）→ 检查任务目标 → 输出**
## 26. 教学代码的可执行性、注释规范与理解性要求

本节作为第 14 节「代码规范」的补充细则，适用于所有涉及程序设计、数据结构、算法及其他包含代码内容的知识整理任务。

**核心原则：代码必须真实可运行、注释必须便于初学者理解、代码之外必须提供必要讲解。代码的首要目标是帮助读者学习，而不是追求形式上的简洁、抽象或高级。**

### 26.1 严格禁止伪代码

除用户明确提出特殊要求外，知识整理中凡涉及代码，一律遵循以下规定：

- **禁止任何形式的伪代码**，不得使用仅用于展示思路、无法实际编译或执行的伪代码替代正式程序。
- 必须使用真实、规范的主流编程语言，包括但不限于 C、C++、Python、Java、JavaScript 等，不强制限定具体语言。
- 代码必须符合所选语言的实际语法规范，具备完整、正确的执行逻辑，不得凭空编造语法、函数、类型或接口。
- 默认提供**完整、能够独立编译或执行的代码**，包括必要的库引用、函数定义、入口函数及相关上下文。
- 如果程序需要多个源文件，应按照真实项目结构分别展示，保证文件之间能够正确配合，最终构成可运行的完整程序。
- 涉及外部依赖、特殊编译选项、运行环境或特定语言版本时，应根据需要说明，避免出现代码看似完整但实际无法运行的情况。

**允许在代码块之外通过自然语言解释算法步骤或执行流程，但不得将自然语言描述、伪造语法或不完整逻辑包装成正式可执行代码。**

### 26.2 逐行注释原则

**默认将读者视为对当前代码及相关语法缺乏充分了解的初学者。**

代码注释应主动解释关键语句的作用，降低读者逐行理解程序的难度。

具体要求：

1. **原则上逐行注释**：对于具有实际功能或教学意义的代码行，应尽可能提供对应注释，尤其是变量定义、函数调用、条件判断、循环、数据操作及关键语法。
2. **优先使用行尾注释**：大多数情况下，注释直接放在对应代码之后，不另起多行进行解释。
3. **保持简洁准确**：普通语句的注释通常只需简短说明其作用，避免冗长、重复或无实际信息的描述。
4. **重要代码允许例外**：对于核心算法、重要语法、易错操作、复杂表达式及容易混淆的执行逻辑，允许在相关语句之前使用独立注释行或连续多行注释进行充分说明。
5. **注释必须具有教学价值**：不仅说明代码表面上进行了什么操作，还应在必要时解释为什么这样写、执行后产生什么效果，以及有哪些需要注意的条件。
6. **避免机械注释**：空行、单纯的括号及不承载独立意义的结构符号，不需要为了追求形式上的逐行注释而强行添加无意义内容。

> **注释密度由学习需要决定：普通代码行简明解释，关键代码行重点解释，复杂代码段允许适当展开。不得为了缩短篇幅而大面积省略教学注释。**

### 26.3 注释语法与兼容性

注释应采用对应编程语言中**最常见、最规范、最易识别且兼容性良好的形式**。

- **C / C++**：默认统一使用 `//` 单行注释，原则上不使用 `/* ... */` 块注释或 `/** ... */` 文档注释。C 语言默认采用支持 `//` 注释的 C99 或更新标准。
- **Python**：优先使用 `#` 进行普通教学注释，不使用多行字符串冒充常规代码注释。
- **Java / JavaScript 等**：普通教学注释优先采用 `//`，不主动引入 Javadoc、JSDoc 等专门的文档注释格式。
- **其他语言**：遵循该语言最普遍、最稳定的注释语法，不为了形式统一而使用不符合语言规范的写法。

注释应保持语句清晰、符号规范、格式统一。避免不必要的特殊字符、复杂排版和可能引起编码兼容问题的装饰性符号。

对于 C / C++ 等可能涉及不同编译环境的语言，应注意源码编码兼容性，优先采用 UTF-8 等通用编码方式，不使用可能造成乱码或编译异常的特殊字符。

### 26.4 严格限制类型别名与不必要的抽象

**教学代码必须优先使用语言原生、具体、直观且普遍认可的数据类型及语法结构，原则上禁止引入不必要的类型别名、抽象包装或人为增加的概念层级。**

尤其针对 C / C++，严格执行以下规定：

1. **原则上禁止使用 `typedef`**，优先直接使用原始数据类型或标准类型名称。
2. 对 C++ 中的 `using` 类型别名采取相同限制，不得通过更换语法形式规避规定。
3. 严禁将 `int`、`float`、`double` 等基础类型人为重命名为 `ADT`、`ElementType` 或其他抽象名称。
4. 不得为了追求代码简洁、专业性、统一性或所谓的高级感，引入没有实际必要的类型别名、包装结构或额外的抽象层。
5. 代码中必须使用具体、真实、符合语言规范的类型。**不得将抽象数据类型（ADT）等理论概念直接作为代码中的类型占位符，也不得为了模拟这些概念而创建没有实际必要的类型别名。**
6. 只有当代码规模较大、类型表达确实复杂，且不使用类型别名会明显造成代码冗长或降低可维护性时，才允许酌情使用。此类例外必须具备充分的实际必要性，而不是出于个人编程习惯。

**必须严格区分理论知识的讲解与实际代码的编写：**

- **理论层面**：允许并应当根据课程需要解释抽象数据类型（ADT）等相关概念，不限制必要的理论教学。
- **代码层面**：必须落实为具体、合法、能够实际编译运行的程序实现。不得仅因理论中存在某种抽象概念，就在代码中人为引入对应的抽象类型名称或多余的包装结构。

例如，在 C 语言中，如果某个数据元素实际上就是 `int`，应直接使用 `int`。不得仅为了对应理论中的抽象数据元素，就额外声明 `typedef int ADT;` 或其他类似别名。

对于类、结构体、模板等语言原生机制，如果它们本身就是当前教学内容或程序实现的必要组成部分，可以正常使用，但不得额外引入脱离教学目标的不必要抽象设计。

**核心原则：理论可以抽象，代码实现必须具体、合法且直观；实际需要什么类型，就优先直接使用什么类型。禁止为了表现抽象而制造抽象，也禁止为了缩短简单代码而牺牲初学者的理解效率。**

### 26.5 代码块之外的教学解释

**严禁出现只有大段代码和少量行内注释，却缺乏正文解释的知识整理方式。**

逐行注释与代码块之外的讲解承担不同任务，两者不能相互替代：

- **行内注释**：主要回答“这一行代码在做什么”。
- **代码块外的解释**：主要回答“为什么这样设计、整体如何运行、涉及哪些知识、如何理解和使用”。

根据代码的重要性及复杂程度，应在代码块前后合理补充以下内容：

1. **功能与目的**：说明程序要解决什么问题、实现什么功能，以及与当前知识点的关系。
2. **关键知识**：介绍理解代码所需的主要语法、数据结构、函数及核心概念。
3. **整体执行逻辑**：解释程序从输入到处理再到输出的主要执行过程，必要时按步骤梳理。
4. **重点语句解析**：对复杂表达式、关键函数、重要操作及初学者容易困惑的语法进行单独解释。
5. **运行方式与结果**：根据需要提供编译、运行方法及具有代表性的输入输出示例。
6. **常见错误与注意事项**：指出典型错误、使用限制及容易混淆的知识点。

上述内容应根据教学价值灵活组织，**不要求每段代码机械包含全部项目，也不要求重复解释已经通过注释充分说明的简单语句。**

对于重要、复杂或具有代表性的代码，应适当提高代码块之外的讲解深度；对于简单代码，则保持精炼。

必要时可结合 Obsidian 的 `[!note]`、`[!example]`、`[!warning]`、`[!tip]` 等 Callout，将代码解释、典型应用与易错提醒进行语义区分，但不得为了视觉效果破坏代码和讲解之间的连续性。

### 26.6 教学友好性与代码设计

在满足正确性、完整性及实际教学要求的前提下，优先选择：

- 更直观的程序结构，而非不必要的复杂架构。
- 更常见的语言语法，而非冷门、晦涩的高级技巧。
- 更容易理解的类型与变量名称，而非过度缩写或抽象命名。
- 更清晰的执行逻辑，而非为了减少代码行数进行过度压缩。
- 更贴近当前课程知识范围的实现方式，而非随意引入大量尚未学习的高级特性。

但**不得将教学友好性错误理解为降低代码正确性或专业规范性**。

不应为了照顾初学者而编写不规范、不安全、已过时或明显不合理的程序；也不应为了展示高级技术而无故增加复杂度。

对于确实需要使用的新语法、新类型或高级知识，应根据需要补充必要解释，而不是直接删除或强行替换。

### 26.7 最终质量检查

凡知识整理内容涉及代码，输出前必须额外检查：

- [ ] 所有代码均为真实语言代码，没有伪代码。
- [ ] 默认提供完整、可编译或可执行的程序。
- [ ] 代码语法正确，必要依赖与运行环境明确。
- [ ] 具有教学意义的代码行基本配有清晰注释。
- [ ] 普通注释优先采用简短的行尾形式。
- [ ] 重要或易错代码得到必要的重点解释。
- [ ] 注释符合语言规范，避免不必要的兼容性问题。
