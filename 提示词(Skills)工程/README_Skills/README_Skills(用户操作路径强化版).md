**# README 编写规范（用户友好增强版）**

你需要为当前项目编写一份**\*\*专业、完整、准确、可长期维护\*\***的 \`README.md\`。

这不是一份简单的项目简介，也不是机械套用 GitHub README 模板。你需要**\*\*先真正理解当前项目，再根据项目实际规模、功能、技术栈、代码结构、使用场景和开发复杂度，自主决定 README 的结构、深度和篇幅\*\***。

README 的核心目标是：

_>_ **\*\*让普通用户能够最快理解“这是什么、能做什么、怎么用”；让开发者能够充分理解“它是怎么实现的、各部分如何协作、为什么这样设计、如何继续开发和维护”。\*\***

README 应当是一份真正服务于项目本身的文档，而不是为了满足某种固定格式而存在的模板。

\---

**# 一、最重要的总体原则**

**## 1. 必须以项目实际内容为依据**

在开始编写 README 之前，必须尽可能充分地检查和理解当前项目。

根据项目情况，应当检查但不限于：

\- 项目源代码；

\- 项目完整目录结构；

\- 程序入口；

\- 配置文件；

\- \`requirements.txt\`、\`package.json\`、\`CMakeLists.txt\` 等依赖或构建文件；

\- 示例代码；

\- 命令行参数；

\- GUI 界面；

\- API 接口；

\- 数据文件；

\- 测试代码；

\- 脚本；

\- 构建方式；

\- 打包方式；

\- 部署方式；

\- LICENSE；

\- 已有文档；

\- 注释；

\- 已有 README；

\- 项目中的版本信息；

\- 项目实际使用的第三方库；

\- 项目实际支持的平台；

\- 项目实际产生的输入和输出。

**\*\*不要根据项目名称、文件名称或少量代码猜测项目功能。\*\***

README 中出现的：

\- 功能；

\- 命令；

\- 参数；

\- 文件名；

\- 目录；

\- API；

\- 依赖；

\- 运行方式；

\- 架构关系；

\- 技术细节；

都应尽可能能够从项目实际内容中得到依据。

如果某项信息无法确认：

\- 不要擅自编造；

\- 不要为了让 README 看起来完整而猜测；

\- 可以直接省略；

\- 如果确实有必要，可以明确标记为“待补充”或“当前项目未提供相关信息”。

**\*\*准确性永远优先于完整性。\*\***

\---

**# 二、绝对不要机械套用模板**

这是本规范中非常重要的一条。

README **\*\*不是固定模板填空题\*\***。

虽然下面会提供很多可以考虑的章节，但它们只是为了提醒你：

_>_ **\*\*一个优秀的 README 通常可能需要考虑哪些方面。\*\***

它们**\*\*不是强制目录，更不是固定顺序\*\***。

你必须根据当前项目自行判断。

例如：

\- 一个几十行的小工具，不需要写成几十页；

\- 一个几百行的小型个人工具，应重点说明用途、安装和使用方式；

\- 一个几千行的个人项目，需要适当说明核心功能、结构和实现；

\- 一个几十个源文件、多个模块组成的项目，应提供较完整的架构和开发者文档；

\- 一个库/API 项目，应重点说明安装、接口和调用方式；

\- 一个命令行工具，应重点说明命令、参数、输入和输出；

\- 一个 GUI 项目，应重点说明界面、操作流程、配置和结果；

\- 一个数据处理项目，应重点说明输入、处理流程、输出格式；

\- 一个网络服务，应重点说明接口、通信流程、部署和配置；

\- 一个课程/学习项目，可以适当说明设计目的和学习内容，但不要把 README 写成课程实验报告；

\- 一个内部个人工具，可能根本不需要贡献指南、路线图等章节。

**\*\*如果你认为当前项目不适合某个章节，可以直接不写。\*\***

反过来，如果项目中存在本规范没有明确列出的重要内容，也应该主动增加相应章节。

**\*\*你按照自己的判断生成的结构，只要最符合当前项目实际情况，就是最好的结构。\*\***

\---

**# 三、“详细”不等于“废话多”**

这是非常重要的要求。

README 可以详细，而且对于复杂项目，应该足够详细。

但是绝对不要通过以下方式制造所谓的“详细”：

\- 重复描述同一个功能；

\- 使用大量空泛形容词；

\- 反复解释显而易见的内容；

\- 把代码逐行翻译成自然语言；

\- 把所有函数都逐个解释一遍；

\- 大段介绍与项目实际使用无关的背景知识；

\- 使用大量“本项目具有……”“通过……可以……”等没有实际信息量的句子；

\- 为了看起来专业而加入没有实际意义的章节；

\- 为了满足固定字数而重复内容；

\- 把项目中很简单的逻辑故意写得复杂。

应该优先增加**\*\*信息密度\*\***。

例如：

_> 一个真实参数、一个实际命令、一个准确的目录说明、一个真实输入输出示例、一个模块之间的依赖关系、一个关键设计原因，都比一大段空泛介绍更有价值。_

**\*\*宁可增加有价值的技术信息，也不要增加没有信息量的文字。\*\***

---

# 四、用户友好性：README 必须提供一条完整、连续的操作路径

这是本规范新增的重点要求。

README 不应只是“信息的集合”，而应该让用户能够沿着文档一步一步完成：

```text
认识项目
  ↓
确认自己的环境是否满足要求
  ↓
准备运行环境
  ↓
安装全部依赖
  ↓
完成必要配置
  ↓
运行项目
  ↓
得到第一次成功结果
  ↓
学习更多用法
  ↓
遇到问题时进行排查
```

**用户友好型 README 的核心不是写更多，而是让“下一步做什么”始终明确。**

## 1. 必须明确区分几个阶段

对于存在环境配置的项目，推荐按照以下逻辑组织用户部分：

### 阶段 0：项目是什么

用户先确认：

- 这个项目解决什么问题；
- 是否适合自己的需求；
- 项目需要什么基本环境。

### 阶段 1：运行前准备

明确告诉用户：

- 需要安装什么软件；
- 需要什么语言版本；
- 是否需要 Git；
- 是否需要 Python / Node.js / Java / C++ 编译器等；
- 是否需要 CUDA、数据库、系统工具或其他外部程序；
- 是否需要准备模型、数据集、配置文件、API Key 等；
- 哪些是必须的，哪些是可选的。

### 阶段 2：安装环境

尽可能提供**完整、可直接复制执行的安装方式**。

例如 Python 项目，如果项目存在 `requirements.txt`，优先：

```bash
pip install -r requirements.txt
```

如果项目没有依赖文件，但可以从项目实际代码中确定依赖，应尽量给出完整安装命令：

```bash
pip install package-a package-b package-c package-d
```

不要只写：

```text
安装所需依赖。
```

也不要只列出：

```text
需要安装：
- package-a
- package-b
- package-c
```

然后把安装动作留给用户自己完成。

**能合并成一条完整命令，就优先提供一条完整命令。**

### 阶段 3：首次运行

必须明确告诉用户：

1. 当前所在目录；
2. 执行什么命令；
3. 是否需要替换路径或参数；
4. 正常情况下应该看到什么；
5. 结果会保存在哪里。

推荐直接形成：

```text
进入项目目录
    ↓
执行环境安装命令
    ↓
执行配置命令（如有）
    ↓
执行启动命令
    ↓
检查输出结果
```

### 阶段 4：正式使用

首次成功运行之后，再介绍：

- 常用参数；
- 不同运行模式；
- 高级功能；
- 输入输出规则；
- 配置项；
- 批量处理；
- 自定义功能。

不要让第一次使用的用户一上来就面对全部高级参数。

### 阶段 5：故障排查

用户遇到问题时，应该能够从 README 快速定位：

```text
问题
 ↓
判断属于哪一类
 ↓
检查环境 / 依赖 / 配置 / 输入
 ↓
执行对应解决方法
 ↓
重新运行
```

---

## 2. README 必须回答“现在该做什么”

用户阅读 README 时，每一个关键阶段都应该具有明确的行动指令。

例如不要只写：

> 本项目依赖 Python 3.x 和若干第三方库。

而应该尽可能写成：

````markdown
## 环境准备

### 1. 安装 Python

本项目需要 Python 3.x。

### 2. 安装依赖

在项目根目录执行：

```bash
pip install -r requirements.txt
```
````

### 3. 启动项目

```bash
python main.py
```

````

即使这些内容看起来简单，也不要认为用户“应该知道”。

---

## 3. 优先提供“一键式”或“少步骤”环境安装

如果项目适合自动化安装，应优先设计或说明一键安装方式。

例如：

### Python

优先使用：

```bash
python -m pip install -r requirements.txt
````

如果还需要创建虚拟环境，并且项目适合这样做，可以提供完整流程：

```bash
python -m venv .venv
```

激活虚拟环境后：

```bash
python -m pip install -r requirements.txt
```

如果项目实际提供安装脚本，例如：

```bash
setup.bat
```

或：

```bash
setup.sh
```

应优先推荐项目自己的安装脚本，并说明其作用。

### Node.js

如果存在：

```text
package.json
```

优先使用项目实际的包管理方式，例如：

```bash
npm install
```

或项目实际采用的：

```bash
npm ci
```

不要同时无意义地列出 npm、yarn、pnpm 三套安装方式，除非项目确实支持并有必要说明。

### C / C++

如果项目依赖 CMake，应明确说明：

```bash
cmake -S . -B build
cmake --build build
```

但**命令必须根据项目实际构建方式生成**，不能机械套用。

### Java

根据实际项目中的 `pom.xml`、`build.gradle` 等文件说明对应构建方式。

---

## 4. “一键安装”不能以牺牲准确性为代价

用户友好并不意味着随便把所有可能的库都塞进安装命令。

必须遵循：

> **只安装项目实际需要的依赖。**

不能因为某个库“可能有用”就加入：

```bash
pip install ...
```

也不能因为某个库曾经被项目使用过，就在当前代码已经不再需要时继续保留。

如果依赖关系复杂，应优先使用项目已有的：

- `requirements.txt`
- `pyproject.toml`
- `poetry.lock`
- `package.json`
- `package-lock.json`
- `CMakeLists.txt`
- `pom.xml`
- `build.gradle`
- 其他实际依赖文件

这些文件是比人工罗列依赖更可靠的依据。

---

## 5. 必须明确“哪些东西用户需要自己准备”

有些项目即使安装完依赖也不能直接运行，例如需要：

- 模型文件；
- 权重文件；
- 数据集；
- 输入 PDF；
- `.env`；
- API Key；
- 数据库；
- 外部程序；
- 特定目录；
- 特定硬件；
- CUDA；
- 浏览器驱动。

此时必须单独列出：

```text
运行前还需要准备：

1. xxx
2. xxx
3. xxx
```

并说明：

- 从哪里获得；
- 放在哪里；
- 文件名是什么；
- 是否必须；
- 如果缺少会发生什么。

**不要让用户运行到一半才发现还缺一个关键文件。**

---

## 6. 首次运行应该是“最短成功路径”

README 应当尽量提供一个：

> **从干净环境开始，到看到第一次成功结果为止的最短路径。**

推荐结构：

````markdown
## 快速开始

### 第 1 步：获取项目

```bash
git clone ...
cd ...
```
````

### 第 2 步：安装环境

```bash
...
```

### 第 3 步：准备必要文件

...

### 第 4 步：运行

```bash
...
```

### 第 5 步：检查结果

正常情况下，你应该看到：

...

````

如果项目不需要 Git，也不要强行加入 `git clone`。

如果项目不能直接运行，也必须明确指出缺少的前置步骤。

---

## 7. Windows、macOS、Linux 的差异必须在真正有差异时说明

如果三个平台命令完全相同，不需要重复三遍。

如果存在差异，应明确写出：

```markdown
### Windows

```powershell
...
````

### macOS / Linux

```bash
...
```

````

尤其注意：

- 路径写法；
- 虚拟环境激活方式；
- shell 命令；
- 编译器；
- 系统依赖；
- 权限；
- 可执行文件；
- GPU / CUDA；
- 外部软件安装方式。

不要只写“支持 Windows / macOS / Linux”，却不给出实际操作差异。

---

## 8. 为长期维护者保留“重新运行项目”的完整路径

README 不只服务第一次使用。

开发者可能几个月后重新打开项目，此时应该能够快速回答：

```text
这个项目当初怎么运行？
需要哪个 Python 版本？
依赖怎么装？
配置文件在哪里？
入口文件是什么？
运行命令是什么？
结果在哪里？
````

因此，对于个人项目尤其应该保留：

```text
环境要求
    ↓
依赖安装
    ↓
配置准备
    ↓
启动命令
    ↓
输出位置
```

**不要因为作者自己熟悉项目，就省略这些步骤。**

---

## 9. 推荐提供“完整安装命令”，而不是让用户拼命令

例如，如果实际依赖为：

```text
PyMuPDF
ultralytics
easyocr
pypdf
```

在没有依赖文件的情况下，优先：

```bash
pip install PyMuPDF ultralytics easyocr pypdf
```

而不是：

```text
请安装 PyMuPDF。
请安装 ultralytics。
请安装 easyocr。
请安装 pypdf。
```

前者让用户复制一次即可完成，后者要求用户自行执行多次操作。

如果存在版本要求，则使用实际项目中能够确认的版本约束，例如：

```bash
pip install "PyMuPDF==..." "ultralytics>=..." ...
```

**不要自行编造版本号。**

---

## 10. 如果项目适合提供安装脚本，应明确说明

如果项目可以安全地提供：

```text
setup.bat
setup.ps1
setup.sh
install.py
```

等脚本，README 可以将其作为推荐入口。

例如：

```text
Windows 用户：
双击 setup.bat
```

或者：

```bash
bash setup.sh
```

但安装脚本本身也必须真实存在。

**README 不应假装项目拥有不存在的“一键安装脚本”。**

---

## 11. 用户友好性不是把所有内容都塞进“快速开始”

快速开始应该短。

推荐形成：

```text
快速开始
    ↓
最短可运行路径

安装与环境
    ↓
完整环境说明

基本使用
    ↓
正常使用方式

高级使用
    ↓
进阶参数与场景

故障排查
    ↓
出现问题时处理
```

这样既不会让新用户被大量信息淹没，也不会让高级用户找不到详细说明。

---

## 12. README 应提供明确的“完成标志”

每个关键步骤最好让用户知道：

> **我怎么知道这一步成功了？**

例如：

```text
安装完成后：

Successfully installed ...

随后执行：

python main.py
```

或者：

```text
运行成功后，项目目录下会生成：

output/
└── result.pdf
```

这比只写“执行以下命令”更加友好。

---

## 13. 对可能失败的步骤提前提醒

如果某一步具有明显的前置条件，应在命令之前说明，而不是等用户报错。

例如：

```text
注意：

执行下面命令前，请确保已经进入项目根目录。
```

或者：

```text
注意：

首次运行需要提前准备 model.pt，并放置在 models/ 目录。
```

这种提醒应放在用户即将执行操作的位置。

---

## 14. 用户部分与开发者部分必须形成明确边界

推荐：

```text
项目介绍
↓
快速开始
↓
环境与安装
↓
基本使用
↓
输入输出
↓
配置
↓
常见问题
────────────
开发者文档
↓
项目结构
↓
架构
↓
模块
↓
数据流
↓
实现
↓
测试
↓
构建
↓
扩展
```

普通用户不需要阅读下面的开发者部分才能运行项目。

**# 五、README 的核心读者**

README 至少需要同时服务两类主要读者：

**## 1. 普通用户**

普通用户最关心：

1\. 这是什么？

2\. 能解决什么问题？

3\. 有什么主要功能？

4\. 需要什么环境？

5\. 如何安装？

6\. 如何运行？

7\. 最简单的使用方法是什么？

8\. 输入什么？

9\. 输出什么？

10\. 常见问题如何解决？

因此用户部分应该：

\- 简洁；

\- 直接；

\- 可操作；

\- 信息密度高；

\- 尽量少讲内部实现；

\- 避免让用户阅读大量开发者内容才能开始使用。

**\*\*普通用户应该能够在很短时间内完成第一次运行。\*\***

\---

**## 2. 开发者**

开发者最关心：

1\. 项目如何组织？

2\. 使用了什么技术？

3\. 核心模块是什么？

4\. 模块之间如何协作？

5\. 程序从哪里开始执行？

6\. 程序主要执行流程是什么？

7\. 数据如何在模块之间流动？

8\. 核心逻辑在哪里？

9\. 关键设计为什么这样实现？

10\. 如何增加功能？

11\. 如何修改现有功能？

12\. 如何替换某个模块？

13\. 如何构建？

14\. 如何测试？

15\. 如何发布或部署？

16\. 当前有什么限制？

因此开发者部分可以明显更加详细。

对于复杂项目，应根据实际情况提供：

\- 项目结构；

\- 技术栈；

\- 系统架构；

\- 模块说明；

\- 执行流程；

\- 数据流；

\- 核心类和函数；

\- 关键设计；

**# 六、用户部分写作要求**

**## 1. 项目简介**

README 开头应该在极短篇幅内回答：

_>_ **\*\*这是什么？解决什么问题？主要面向谁？\*\***

第一眼看到 README 的用户不应该需要阅读数百字才能知道项目用途。

可以采用：

\`\`\`markdown

**# 项目名称**

一句话说明项目用途。

简短补充说明核心能力、主要使用场景以及项目定位。

\`\`\`

不要在开头写大段背景故事。

\---

**## 2. 主要功能**

只列出真正重要的功能。

例如：

\`\`\`markdown

**## 主要功能**

\- 功能 A：具体解决什么问题

\- 功能 B：具体解决什么问题

\- 功能 C：支持什么输入或输出

\- 功能 D：提供什么特殊能力

\`\`\`

避免：

\`\`\`text

\- 简单易用

\- 功能强大

\- 高效稳定

\- 设计优秀

\- 性能卓越

\`\`\`

除非能够提供实际依据，否则不要使用这种宣传式描述。

README 是技术文档，不是广告。

\---

**## 3. 快速开始**

这是用户部分最重要的内容之一。

应该尽可能让用户完成：

_>_ **\*\*安装 → 运行 → 得到结果\*\***

例如：

\`\`\`bash

cd ...

pip install -r requirements.txt

python main.py

\`\`\`

如果项目不需要安装，应明确说明。

如果存在多种运行方式：

\- 优先展示最常用、最简单的一种；

\- 其他方式放到后续章节；

\- 不要一开始就把所有高级选项堆给新用户。

\- 安装命令；

\- 虚拟环境要求；

\- 外部软件；

\- 环境变量；

\- 特殊系统配置。

例如：

\`\`\`markdown

**### Windows**

...

**### macOS**

...

**### Linux**

...

\`\`\`

但是如果三个平台完全一致，则没有必要重复三遍。

**\*\*不要列出项目实际上没有使用的依赖。\*\***

\---

**## 5. 使用方法**

必须基于项目实际功能编写。

如果是命令行程序：

\`\`\`bash

\`\`\`

并解释实际参数：

\| 参数    | 说明 | 默认值 |

\| ------- | ---- | ------ |

\| \`--xxx\` | xxx  | xxx    |

4\. 每个重要按钮或区域的作用；

如果是 Python/C++/Java 等库：

提供最小可运行示例。

**## 7. 实际示例**

\`\`\`

\`\`\`

原因：

\`\`\`

**# 七、开发者部分写作要求**

开发者部分是本 README 与普通项目介绍最重要的区别。

对于复杂项目，这一部分应该明显比用户部分更加深入。

\---

**## 1. 项目结构**

根据实际目录生成项目结构。

例如：

\`\`\`text

project/

├── src/

│   ├── core/

│   ├── utils/

│   └── ...

├── tests/

├── docs/

├── examples/

├── README.md

├── requirements.txt

└── LICENSE

\`\`\`

然后解释重要目录和文件：

\| 路径         | 作用     |

\| ------------ | -------- |

\| \`src/core/\`  | 核心逻辑 |

\| \`src/utils/\` | 通用工具 |

\| \`tests/\`     | 测试     |

\| \`main.py\`    | 程序入口 |

**\*\*不要把每一个无意义的小文件都解释一遍。\*\***

但如果某个看起来普通的文件实际上承担重要职责，则应当说明。

\---

**## 2. 技术栈**

明确列出项目实际使用的技术。

例如：

\`\`\`markdown

\- 编程语言：Python 3.x

\- 图形界面：PySide6

\- PDF 处理：PyMuPDF

\- 构建工具：...

\- 测试框架：...

\`\`\`

尽可能使用中文描述。

如果存在标准技术名称，可以保留英文，例如：

\- Python；

\- C++；

\- PySide6；

\- PyMuPDF；

\- CMake；

\- Git；

不要为了中文化而强行翻译这些正式技术名称。

如果某项只是开发工具，而不是程序运行时依赖，应当明确区分。

\---

**## 3. 系统架构**

对于存在一定复杂度的项目，需要说明整体架构。

重点回答：

_>_ **\*\*程序由哪些核心部分组成？这些部分之间如何协作？\*\***

可以使用：

\`\`\`text

输入

  ↓

解析

  ↓

核心逻辑

  ↓

处理

  ↓

输出

\`\`\`

如果适合，可以使用 Mermaid：

\`\`\`mermaid

    A[输入] --> B[解析]

    B --> C[核心逻辑]

    C --> D[输出]

\`\`\`

不要为了“看起来专业”而强行使用 Mermaid。

如果简单文字或目录结构已经足够清楚，就不要额外制造复杂图表。

\---

**## 4. 核心执行流程**

说明程序从启动到结束的大致过程。

例如：

\`\`\`text

程序启动

→ 加载配置

→ 验证输入

→ 读取数据

→ 核心处理

→ 生成结果

→ 保存或展示结果

\`\`\`

对于复杂项目，应进一步说明：

\- 初始化；

\- 关键分支；

\- 模块调用顺序；

\- 异常路径；

\- 程序退出流程。

\---

**## 5. 核心模块**

逐个解释真正重要的模块。

每个模块至少可以说明：

\- 职责；

\- 输入；

\- 输出；

\- 与其他模块的关系；

\- 关键实现方式；

\- 是否可以独立替换；

\- 其他开发者修改时需要注意什么。

**\*\*不要逐行解释代码。\*\***

README 需要解释代码结构和设计，而不是代替源代码。

\---

**## 6. 核心数据流**

如果项目存在明显的数据流，应当解释：

\`\`\`text

输入数据

↓

解析

↓

内部数据结构

↓

核心处理

↓

结果对象

↓

输出文件

\`\`\`

重点说明：

\- 数据从哪里产生；

\- 使用什么结构保存；

\- 在哪里转换；

\- 哪个模块处理；

\- 最终如何输出。

对于复杂项目，这部分往往比单纯的目录说明更加重要。

\---

**## 7. 关键设计与实现**

对于值得开发者理解的设计，应解释：

\- 为什么采用当前实现方案；

\- 为什么使用某个库；

\- 为什么采用某种数据结构；

\- 为什么代码拆分成当前模块；

\- 哪些设计是为了兼容性；

\- 哪些设计是为了可维护性；

\- 哪些地方存在技术权衡；

\- 哪些实现存在特殊处理。

但是必须特别注意：

**\*\*不要编造作者没有做过的设计决策。\*\***

如果无法确定作者为什么这么设计，可以客观描述：

_> “当前实现采用……”_

而不要写成：

_> “作者为了提高性能，所以……”_

除非代码或其他项目资料能够支持这种判断。

\---

**## 8. 接口、类与函数**

如果项目存在公开 API、类、函数、命令行接口等，应提供开发者级说明。

例如：

\`\`\`markdown

**### \`parse_document(path)\`**

读取并解析指定文件。

**\*\*参数\*\***

\- \`path\`：输入文件路径。

**\*\*返回值\*\***

解析后的文档对象。

**\*\*异常\*\***

...

\`\`\`

对于类，可以说明：

\- 类的职责；

\- 成员；

\- 构造方式；

\- 重要方法；

\- 输入输出；

\- 使用关系。

但不要把每个简单 getter/setter 都写成长篇说明。

**\*\*说明深度应与接口的重要程度匹配。\*\***

\---

**## 9. 错误处理**

如果项目存在比较明确的异常处理机制，应说明：

\- 错误类型；

\- 错误产生位置；

\- 错误传播方式；

\- 用户看到什么；

\- 开发者如何定位；

\- 日志在哪里；

\- 是否会自动恢复。

\---

**## 10. 测试**

如果项目存在测试，应说明：

\- 使用什么测试框架；

\- 测试目录在哪里；

\- 如何运行；

\- 测试覆盖哪些核心功能；

\- 是否存在测试数据；

\- 是否有特殊测试环境要求。

例如：

\`\`\`bash

pytest

\`\`\`

如果没有测试：

**\*\*不要虚构测试体系。\*\***

可以客观说明：

_> 当前项目暂无自动化测试。_

如果存在部分手工测试，也可以说明实际情况。

\---

**## 11. 开发环境**

如果项目具有明确的开发环境，应说明：

\- 编程语言版本；

\- IDE；

\- 编译器；

\- 构建工具；

\- 包管理器；

\- 必要 SDK；

\- 操作系统；

\- 开发依赖。

区分：

_>_ **\*\*运行项目所需环境\*\***

和：

_>_ **\*\*参与开发所需环境\*\***

两者不要混在一起。

\---

**## 12. 构建、打包、发布与部署**

如果项目存在编译、构建、打包、发布或部署流程，应根据实际情况说明：

\- 开发环境；

\- 构建命令；

\- 构建过程；

\- 输出产物；

\- 打包方式；

\- 发布流程；

\- 部署方法；

\- 平台差异。

不要因为某个项目没有发布流程，就强行创建一个“发布”章节。

例如一个普通 Python 脚本，如果只是直接运行：

\`\`\`bash

python main.py

\`\`\`

就没有必要虚构复杂的“部署架构”。

\---

**## 13. 扩展与二次开发**

对于具有持续开发价值的项目，应说明：

_>_ **\*\*如果开发者想增加一个新功能，应该从哪里开始？\*\***

例如：

\`\`\`text

新增处理器

→ 创建新模块

→ 实现统一接口

→ 注册到对应模块

→ 添加测试

→ 更新配置

\`\`\`

如果项目使用插件机制、注册表、工厂模式等，也应该根据实际实现说明。

这一部分对于长期维护尤其重要。

**# 八、复杂项目的额外要求**

如果项目规模较大，应当自动增加 README 深度。

例如项目具有：

\- 多个核心模块；

\- 多种输入输出；

\- GUI + 命令行；

\- 数据库；

\- 网络服务；

\- 插件系统；

\- 多线程/异步；

\- 复杂配置；

\- 多平台支持；

\- 编译系统；

\- 多个外部依赖；

则不能只写：

_> 项目简介 + 安装方法 + 简单目录。_

应根据实际情况增加：

\- 系统架构；

\- 模块关系；

\- 数据流；

\- 生命周期；

\- 配置系统；

\- 接口；

\- 扩展机制；

\- 构建系统；

\- 测试体系；

\- 部署方式；

\- 性能相关注意事项；

\- 平台兼容性；

\- 已知限制；

\- 重要设计取舍。

如果项目规模非常大，可以进一步按照模块拆分开发者文档，但 README 本身仍然应当承担“总入口”的职责。

\---

**# 九、篇幅控制原则**

README **\*\*没有固定字数限制\*\***。

应该遵循：

_>_ **\*\*最小项目，最小文档；复杂项目，完整文档。\*\***

不要为了“详细”强行写长，也不要因为害怕 README 太长而删除真正有价值的信息。

尤其注意：

**### 宁可增加技术信息，也不要增加空泛描述。**

一个包含 20 个源文件的项目，README 比一个 100 行脚本长很多是正常的。

一个拥有复杂架构的项目，README 达到数千字甚至更多也是合理的。

但是：

_>_ **\*\*README 的目标不是尽可能长，而是让信息密度尽可能高。\*\***

如果某段内容不能帮助：

\- 用户使用项目；

\- 开发者理解项目；

\- 开发者维护项目；

\- 开发者扩展项目；

那么就应该考虑删除。

\---

**# 十、README 中的代码、命令与项目结构**

所有代码、命令、路径、参数必须尽量来自实际项目。

代码块应注明语言：

\`\`\`bash

python main.py

\`\`\`

\`\`\`python

from xxx import xxx

\`\`\`

路径必须与项目实际结构一致。

不要出现：

\`\`\`text

your_project/

your_file.py

some_command

\`\`\`

这种仅用于凑格式的占位内容，除非确实需要用户自行替换。

如果确实存在需要用户替换的变量，应明确说明：

\`\`\`bash

python main.py <你的文件路径>

\`\`\`

而不是假装这是一个真实文件名。

\---

**# 十一、版本与兼容性**

如果项目能够确定版本信息，应说明：

\- 当前版本；

\- 支持的语言版本；

\- 支持的操作系统；

\- 关键依赖版本；

\- 已测试的平台；

\- 平台之间存在的差异。

如果无法确认，不要自行编造版本号。

如果代码实际上没有进行跨平台测试，也不要写：

_> “完全支持 Windows、macOS 和 Linux。”_

可以客观描述当前能够确认的信息。

\---

**# 十二、截图、GIF、示意图与可视化内容**

如果项目是：

\- GUI；

\- 可视化工具；

\- 图像处理工具；

\- 数据分析工具；

\- 具有明显交互界面的应用；

应考虑是否需要加入：

\- 截图；

\- GIF；

\- 架构图；

\- 流程图；

\- 输出示例。

但只有在这些内容能够真正帮助用户理解项目时才加入。

不要为了“看起来专业”而加入没有信息价值的图片。

如果当前环境无法获得真实截图，也不要伪造截图。

\---

**# 十三、许可证**

> 所有的 README 一律采用如下声明：

License
本项目代码仅供学习、研究与个人使用。未经作者许可，禁止将本项目用于商业用途、直接复制后重新发布，或以本项目及其衍生代码作为独立项目进行再发布。
**# 十四、开发路线**

只有当项目确实存在未来计划时才写。

不要虚构开发计划。

如果项目已经稳定，或者作者没有明确的未来计划，可以不写这一部分。

如果项目确实存在路线图，应当只记录能够从项目资料中确认的内容。

**# 十五、参与开发**

如果项目是个人小工具：

不需要为了套模板强行加入复杂的贡献指南。

如果项目具有多人协作或开源属性，则可以说明：

\- Issue；

\- Pull Request；

\- 开发规范；

\- 测试要求；

\- Commit 规范；

\- 分支策略；

\- 代码风格；

\- 提交要求。

所有内容以项目实际情况为准。

**# 十六、语言与表达风格**

README 默认使用**\*\*中文\*\***编写。

整体风格要求：

\- 专业；

\- 清晰；

\- 克制；

\- 信息密度高；

\- 技术准确；

\- 易于扫描；

\- 不故作高深；

\- 不营销化；

\- 不写论文腔；

\- 不写流水账。

优先使用：

\- 中文标题；

\- 小标题；

\- 表格；

\- 列表；

\- 代码块；

\- 简短段落。

正式技术名称、库名称、命令、API、类名、函数名等可以保留英文。

例如：

_> 使用 \`PyMuPDF\` 处理 PDF 文件。_

而不是强行翻译技术名称。

避免连续的大段文字。

**# 十七、README 的阅读层次**

最终 README 应形成明显的阅读层次：

\`\`\`text

第一层：我第一次看到这个项目

        ↓

        知道它是什么、能干什么

第二层：我想使用它

        ↓

        能快速安装并运行

第三层：我想深入使用

        ↓

        知道参数、配置、输入输出

第四层：我想开发它

        ↓

        理解目录、模块、架构和数据流

第五层：我想维护 / 扩展它

        ↓

        理解设计、测试、构建和扩展方式

\`\`\`

README 不应该要求普通用户阅读完整篇文档才能开始使用。

同时，开发者也不应该因为 README 过度简略，而必须自行阅读大量源代码才能弄清楚项目的大致结构。

**# 十八、README 的信息优先级**

如果需要在“完整”和“简洁”之间进行取舍，应优先保留以下信息：

**### 第一优先级：项目是什么**

\- 项目用途；

\- 核心功能；

\- 适用场景。

**### 第二优先级：怎么使用**

\- 环境；

\- 安装；

\- 快速开始；

\- 基本用法；

\- 输入输出。

**### 第三优先级：怎么理解**

\- 项目结构；

\- 技术栈；

\- 架构；

\- 核心模块；

\- 执行流程。

**### 第四优先级：怎么继续开发**

\- 接口；

\- 设计；

\- 测试；

\- 构建；

\- 扩展；

\- 部署。

这并不意味着第四优先级内容不重要，而是意味着**\*\*如果项目规模很小，不应该为了写满这些内容而强行制造内容。\*\***

**# 十九、必须区分“事实”和“推测”**

这是技术 README 中非常容易出现的问题。

以下内容属于事实：

_> 项目使用 PyMuPDF。_

如果可以从依赖文件或源代码确认，就可以直接写。

以下属于推测：

_> 作者使用 PyMuPDF 是为了提高 PDF 处理性能。_

除非项目文档或其他明确资料能够支持，否则不要这样写。

类似地：

不要擅自声称：

\- “这是为了性能优化”；

\- “这是为了提高安全性”；

\- “这是为了方便维护”；

\- “作者采用这个结构是因为……”。

如果无法确定原因，可以改成：

_> 当前实现使用……_

或者：

_> 当前代码将……划分为……_

**\*\*README 应该记录项目，而不是替作者编造项目设计思想。\*\***

**# 二十、已有 README 的处理方式**

如果当前项目已经存在 README：

**\*\*不要无视原 README，直接从零重新生成。\*\***

应当：

1\. 阅读原 README；

2\. 理解原作者已经提供的信息；

3\. 与当前代码和项目结构进行核对；

4\. 保留仍然准确、有价值的内容；

5\. 修正过时内容；

6\. 补充缺失内容；

7\. 重组结构；

8\. 删除重复、空泛和错误内容。

最终目标是得到一份更好的 README，而不是简单地“覆盖旧 README”。

\---

**# 二十一、信息缺失时的处理方式**

如果 README 中应该出现某项信息，但当前项目无法确认：

**### 可以确认**

直接写。

**### 可以从代码合理推断，但不是绝对确定**

使用客观、保守的表达。

**### 完全无法确认**

不要编造。

可以：

\- 省略；

\- 标记“待补充”；

\- 或在文档适当位置说明“当前项目未提供相关信息”。

**\*\*不要为了让 README 看起来完整而制造事实。\*\***

# 二十四、用户操作链最终检查

在生成 README 前，必须从一个**完全不了解项目的新用户**视角，把实际操作链重新走一遍。

至少检查：

```text
我拿到项目后
    ↓
我知道它是什么了吗？
    ↓
我知道需要什么环境了吗？
    ↓
我知道应该先安装什么了吗？
    ↓
我能一次性安装全部必要依赖吗？
    ↓
我知道还需要准备哪些文件 / 配置了吗？
    ↓
我知道命令应该在哪个目录执行了吗？
    ↓
我能直接复制命令吗？
    ↓
我知道运行命令是什么了吗？
    ↓
我知道什么现象代表运行成功了吗？
    ↓
我知道输出在哪里了吗？
    ↓
出错后我知道应该先检查什么了吗？
```

如果其中任何一个关键环节只能依靠用户“自己猜”“自己搜索”或“自己看源码”，应优先补充 README。

尤其注意以下几类问题：

### 1. 依赖安装不完整

错误：

```text
需要安装 PyMuPDF、EasyOCR、YOLOv8 等依赖。
```

更好的形式：

```bash
python -m pip install -r requirements.txt
```

或者，在确实没有依赖文件且能够确认依赖的情况下：

```bash
python -m pip install PyMuPDF easyocr ultralytics ...
```

### 2. 环境准备被拆散

错误：

```text
需要 Python。
需要模型。
需要配置文件。
然后运行程序。
```

应该整理成连续流程：

```text
1. 安装 Python
2. 创建虚拟环境
3. 安装依赖
4. 准备模型文件
5. 修改配置
6. 运行程序
```

### 3. 只给启动命令，不解释运行位置

错误：

```bash
python main.py
```

应在必要时说明：

````text
进入项目根目录后执行：

```bash
python main.py
````

````

### 4. 只告诉用户“成功”，却不说明如何判断成功

应尽量提供：

- 终端中的正常输出；
- 生成的文件；
- 输出目录；
- GUI 中应该出现的界面；
- 其他可验证结果。

### 5. 一键安装脚本与实际项目不一致

如果项目没有：

```text
setup.bat
install.sh
````

就不能写：

```text
运行 setup.bat 即可完成安装。
```

如果项目已有安装脚本，应说明：

- 脚本名称；
- 适用平台；
- 脚本执行了什么；
- 执行完成后下一步是什么。

# 二十五、关于“一键安装”的进一步规范

“一键安装”应理解为：

> **尽可能减少用户需要自己判断、拆分和重复输入的操作。**

不一定非要真的只有一个脚本。

可以根据项目实际情况采用：

### 方式 A：依赖文件

```bash
python -m pip install -r requirements.txt
```

### 方式 B：完整单条命令

```bash
python -m pip install package-a package-b package-c
```

### 方式 C：安装脚本

```bash
setup.bat
```

或：

```bash
bash setup.sh
```

### 方式 D：标准项目安装方式

例如实际存在 `pyproject.toml` 时，根据项目实际配置使用：

```bash
python -m pip install .
```

### 方式 E：完整环境脚本

如果项目本身提供从环境创建到依赖安装的一整套脚本，可以直接将其作为推荐入口。

**选择哪一种必须由项目实际情况决定。**

不要为了“用户友好”而额外制造一个实际上没有必要的安装系统。

# 二十六、不要把 README 写成“知识考试”

用户执行项目时，不应该被迫回答：

```text
Python 应该用 pip 还是 pip3？
应该进入哪个目录？
requirements.txt 应该怎么安装？
这个模型文件放哪里？
这个参数是不是必须？
这个脚本先运行还是后运行？
```

如果这些问题可以由 README 根据项目实际情况明确回答，就应该直接回答。

**README 的职责之一，就是替用户消除这些不必要的决策成本。**

但对于确实存在多个合理方案的地方，应明确说明差异，而不是假装只有一种方案。

**# 二十七、最终要求**

请把这次任务理解为：

_>_ **\*\*为这个项目制作一份真正可以放进 GitHub / GitLab 项目根目录、供用户和开发者长期使用的正式 README。\*\***

不要把任务理解为：

_> “按照固定模板生成一篇 README。”_

更不要因为本规范列出了很多章节，就认为这些章节全部必须出现。

**\*\*规范提供的是判断标准，而不是固定答案。\*\***

最终文档应该做到：

**\*\*用户看前面很短的一部分，就能理解项目是什么、有什么用，并开始使用；\*\***

**\*\*用户继续阅读，可以获得完整的安装、使用、配置和输入输出信息；\*\***

**\*\*开发者继续往下阅读，可以逐步理解项目结构、技术栈、架构、模块、数据流、实现方式和维护方法；\*\***

**\*\*项目越复杂，开发者部分越详细；项目越简单，则保持克制；\*\***

**\*\*信息宁可完整，也不能敷衍；但是绝不通过重复、套话和无意义章节制造所谓的“详细”。\*\***

最重要的是：

_>_ **\*\*先理解项目，再决定怎么写 README。\*\***

_>_

_>_ **\*\*不要先决定 README 应该长什么样，再强行把项目塞进模板。\*\***

如果当前项目已经存在 README，应当在充分理解原 README 后进行**\*\*重构、补充和改进\*\***，而不是无视已有内容直接覆盖。

如果项目中存在明显缺失但无法从代码确认的信息，应明确指出缺失项，而不是自行编造。

**\*\*最终只输出完整的 \`README.md\` 内容。\*\***

不要输出分析过程。

不要解释你准备如何写。

不要先给出大纲后等待确认。

不要告诉用户“下面我将……”。

直接完成 README。

**# 二十三、流程图、架构图与特殊标记语言**

README 中如果需要表达：

\- 程序执行流程；

\- 数据流；

\- 模块调用关系；

\- 系统架构；

\- 文件处理流程；

\- 用户操作流程；

**\*\*优先使用纯 Markdown 文本、列表以及 ASCII 风格的文字和箭头表达。\*\***

例如：

\`\`\`text

原始 PDF

  ↓

逐页读取

  ↓

图像处理

  ↓

目标检测

  ↓

文字识别

  ↓

层级修复

  ↓

生成书签

  ↓

输出 PDF

\`\`\`

或者：

\`\`\`text

输入文件 → 文件解析 → 数据处理 → 结果生成 → 输出文件

\`\`\`

这种形式具有更好的：

\- 跨平台兼容性；

\- GitHub / GitLab / 本地 Markdown 编辑器兼容性；

\- 可读性；

\- 可复制性；

\- 长期维护性。

**### 特殊图表语言**

除非项目本身明确要求，否则**\*\*不要使用 Mermaid、PlantUML、Graphviz DOT 等需要特定渲染器或额外支持的图表语言\*\***。

尤其不要为了让 README “看起来更专业”而强行使用：

\`\`\`mermaid

flowchart LR

    A --> B

\`\`\`

这类特殊语法。

如果使用纯文本已经能够清晰表达关系，就应当优先使用纯文本。

只有当项目实际复杂到纯文本难以准确表达，并且确实需要图形化展示时，才考虑使用真实图片或项目已有的图表资源；**\*\*不要为了图表而引入额外的文档语法依赖。\*\***

总体原则：

_>_ **\*\*README 中的流程、架构和数据关系，优先采用最简单、最通用、无需额外渲染器即可阅读的文本表达方式。\*\***
